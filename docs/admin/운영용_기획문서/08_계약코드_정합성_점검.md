# 계약코드 정합성 점검

점검일: 2026-05-20

기준 시트:
- `개발사 계약 및 상세 기능리스트_제로스트 피드백_260518`
- 탭: `1.제로스트계약_기능리스트`
- 기준 열: B열 `기능 코드`

비교 시트:
- `개발사 계약 및 상세 기능리스트_제로스트 피드백_260518`
- 탭: `3.CRM (admin)_제로스트_0518논의`
- 비교 열: D열 `계약 코드`
- 비교 열: F열 `기획 MD파일 기획 코드`

## 원칙

1. 최초 계약 기준 코드는 `1.제로스트계약_기능리스트` 탭의 B열 `기능 코드`를 정본으로 본다.
2. `3.CRM (admin)_제로스트_0518논의` 탭의 D열 `계약 코드`는 최초 계약코드와 동일해야 하는 비교/매핑 열로 본다.
3. 기존 계약 항목에 대응되는 기획은 계약코드를 우선 사용한다.
4. 신규 기획코드가 필요한 경우, 기존 계약코드 전체와 중복되면 안 된다.
5. 기획 기능 하나가 계약코드 여러 개를 포괄하는 경우, 단순 치환하지 않고 계약코드별 alias 또는 기능명세서 분리를 먼저 결정한다.
6. 기능명세서 `id`, 화면설계서 `feature_codes`, Cmd+/ 연결은 같은 코드 체계를 따라야 한다.
7. 현재 문서에 이미 존재하는 추가 기획 후보는 별도 `신규기획` 라벨을 붙이지 않는다.
8. 이 점검 이후 새로 추가되는 기능명세서는 `contract_codes`가 없으면 `contract_status`를 `신규기획`, `비계약`, `파생기획` 중 하나로 명시한다.

## 계약코드 미연결 처리 기준

계약코드를 임의로 붙이지 않는다. 현재 존재하는 추가 기획 후보 39개는 문서에 `신규기획`이라고 명시하지 않고, `scripts/check-contract-codes.ts`의 `LEGACY_UNCLASSIFIED_IDS`에만 고정해 검증 예외로 둔다.

- `신규기획`: 이 점검 이후 새로 추가되는 기능명세서 중 기존 계약코드 136개에 없는 추가 기획. 향후 계약 범위에 포함하려면 기존 계약코드와 중복되지 않는 신규 코드 발급 필요.
- `비계약`: 공통 화면, 공통 다이얼로그, 내부 운영 보조 기능처럼 계약 잔금 산정 단위로 직접 쓰지 않는 항목.
- `파생기획`: 기존 계약 기능을 운영/설정 화면으로 확장한 항목. 대표 계약코드는 본체 기능명세서에만 유지.

현재 미분류 허용 목록에 없는 기능명세서가 새로 생기고, `contract_codes`와 `contract_status`가 모두 없으면 `scripts/check-contract-codes.ts`에서 경고가 발생한다.

## 중복 계약코드 귀속 결정

### MKT-02

- 계약 기능명: 자동 알림 13종 엔진
- 대표 기획: `MKT-02` 자동 알림 설정
- 파생 기획: `SET-EXT-01` 지점 자동화 적용, `HQ-09` 자동화 정책 라이브러리

`MKT-02`는 자동 알림 엔진 자체를 의미하므로 `D08-마케팅/MKT-02-자동알림`에만 `contract_codes: [MKT-02]`를 유지한다. `SET-EXT-01`과 `HQ-09`는 같은 엔진을 지점/본사 운영 화면으로 확장한 파생 기획이므로 계약코드 alias를 제거한다. 향후 별도 잔금 또는 추가 개발 범위로 분리해야 하면 기존 계약코드와 중복되지 않는 신규 코드로 발급한다.

### RSV-04

- 계약 기능명: 출결 처리
- 대표 기획: `IoT-07` 통합 출석 관리
- 파생 기획: `SET-EXT-05` 출석 관리 설정

`RSV-04`는 출석/결석/노쇼/지각을 처리하는 운영 기능이므로 `D11-통합운영/IoT-07-통합출석관리`에만 `contract_codes: [RSV-04]`를 유지한다. `SET-EXT-05`는 출결 처리의 기준값을 관리하는 설정 화면이므로 계약코드 alias를 제거한다. 향후 설정 기능을 별도 계약 항목으로 산정해야 하면 기존 계약코드와 중복되지 않는 신규 코드로 발급한다.

## 기능명세서 id 기준 재정렬 후보

현재 기능명세서 `id`가 계약코드에 없고 기획코드에만 존재하는 대표 항목:

`MKT-08`, `SET-EXT-04`, `SET-EXT-01`, `SET-EXT-05`, `FAC-05`, `PRD-08`, `FAC-01`, `FAC-03`, `IoT-05`, `STF-EXT-01`, `FAC-EXT-01`, `IoT-04`, `FAC-06`, `HQ-EXT-06`, `PAY-06`, `CLS-11`, `IoT-07`, `FAC-02`, `HQ-09`, `IoT-03`, `IoT-06`, `PRD-EXT-01`, `CLS-14`, `PRD-04`, `CLS-12`, `PRD-EXT-02`, `FAC-04`, `CLS-13`, `SAL-EXT-05`, `CLS-10`

처리 원칙:
- 계약 범위 내 기능이면 기능명세서 `id`를 계약코드로 재배정하거나 `contract_codes` alias를 도입한다.
- 계약 범위 밖 신규 기능이면 새 기획코드를 유지하되 계약코드 전체와 중복되지 않는 prefix를 사용한다.
- 하나의 기획 기능이 여러 계약코드를 포괄하면 기능명세서를 계약코드별로 분리할지, 하나의 문서에 복수 `contract_codes`를 둘지 먼저 결정한다.

## 다음 작업 제안

1. 기능명세서 frontmatter에 `contract_codes` 필드를 추가하는 스키마를 확정한다.
2. `scripts/check-feature-codes.ts` 또는 별도 스크립트에서 다음을 검증한다.
   - 신규 기획코드가 계약코드와 중복되지 않는지
   - 계약코드가 있는 행은 기능명세서 `id` 또는 `contract_codes`에 반드시 연결되는지
   - 하나의 계약코드가 여러 기획코드에 연결된 경우 명시적으로 허용 목록에 있는지
3. 대량 rename은 바로 하지 말고, 먼저 42개 Lv1 불일치 매핑을 계약코드 기준으로 확정한다.
4. 이후 화면설계서 `feature_codes`와 기능명세서 `id`를 같은 단위로 변경한다.
