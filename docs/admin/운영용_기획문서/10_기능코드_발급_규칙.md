# 기능코드 발급 규칙

기준일: 2026-05-20

## 핵심 원칙

1. 0508 기획에 이미 존재한 기능코드는 원래 의미를 유지한다.
2. 기존 코드의 명칭만 다듬는 수준이면 같은 코드를 유지한다.
3. 기존 코드에 다른 기능이 들어가면 코드 변경이 아니라 삭제+신규 추가로 처리한다.
4. 0508 이후 새로 추가된 기획은 기존 계약코드와 기존 기획코드를 재사용하지 않는다.
5. 신규 기능코드는 같은 prefix 안에서 사용 중인 마지막 번호 다음 번호로 발급한다.
6. 계약 잔금 기준은 계약코드이므로, 기능명세서에는 `contract_codes` 또는 `contract_status`를 명시한다.

## 코드 유지 / 변경 판단

| 상황 | 처리 | 예시 |
|---|---|---|
| 명칭만 보강 | 기존 코드 유지 | `포인트` → `플랫폼 잔여 캐시`처럼 같은 행위의 용어 보정 |
| 설명이 상세화됨 | 기존 코드 유지 가능 | `외부 연동` → 연동 대상 목록 추가 |
| 화면 위치만 이동 | 코드 이동 | `KINF-01` → `MBI-01`, 단 기능 의미가 같아야 함 |
| 기능 목적이 바뀜 | 기존 코드 삭제 + 신규 코드 발급 | `IoT-01` 키오스크 설정 자리에 통합 출석 관리 입력 금지 |
| 기존 기능 아래 새 하위기능 추가 | 같은 parent의 다음 하위번호 발급 | `IoT-07-06` 다음은 `IoT-07-07` |
| 새 Lv1 기능 추가 | 같은 prefix의 다음 Lv1 번호 발급 | `IoT-06`까지 있으면 신규는 `IoT-07` |

## 의미 변경 기준

다음 중 하나라도 해당하면 기존 코드 재사용 금지:

- 사용자가 수행하는 주 업무가 달라진다.
- 화면의 목적이 설정에서 운영, 조회에서 처리, 목록에서 결제처럼 바뀐다.
- 기존 0508 명칭과 0518 명칭의 의미 유사도가 낮다.
- 기존 하위 구조가 대부분 사라지고 다른 하위 구조가 들어간다.
- 기존 계약코드의 잔금 산정 대상과 다른 기능이 들어간다.

판단이 애매하면 기존 코드를 유지하지 말고 신규 코드 후보로 둔다.

## 신규 번호 발급 방식

### Lv1

1. 같은 prefix의 기존 Lv1 코드를 모두 확인한다.
2. 0508 기준 코드와 현재 로컬 기능명세서 코드를 함께 본다.
3. 가장 큰 번호 다음 번호를 사용한다.
4. 중간에 비어 있는 번호가 있어도 과거 사용 이력이 있으면 재사용하지 않는다.

예시:

```text
0508 기준:
IoT-01 = 키오스크 설정
IoT-02 = IoT 출입 관리
IoT-03 = IoT 연동 관리
IoT-04 = 옷 락커 운영 관리
IoT-05 = 회원 건강 연동 요약
IoT-06 = 키오스크 운영 현황

신규 통합 출석 관리 = IoT-07
신규 통합 운영 키오스크 설정 = IoT-08
```

### Lv2 / Lv3

1. parent 코드의 기존 하위번호를 확인한다.
2. 같은 depth의 마지막 번호 다음을 사용한다.
3. 기존 하위번호의 의미를 바꾸지 않는다.

예시:

```text
IoT-07-06 = 키오스크 모니터
IoT-07-07 = 실패 로그
IoT-07-08 = 외부 연동
IoT-07-09 = 실시간 출석 확인 카드
```

## 계약코드와 기획코드 관계

| 구분 | 규칙 |
|---|---|
| 계약 범위 본기능 | 기능명세서 `contract_codes`에 계약코드 명시 |
| 계약 기능의 설정/운영 파생 | `contract_status: 파생기획` 또는 대표 기능에만 계약코드 유지 |
| 비계약 공통/인프라 | `contract_status: 비계약` |
| 새 추가기획 | `contract_status: 신규기획`, 단 기존 계약코드와 중복 금지 |

하나의 기획이 여러 계약코드를 대표하면 다음 중 하나로 결정한다.

- 기능명세서 하나에 복수 `contract_codes`를 둔다.
- 계약코드별 기능명세서로 분리한다.
- 대표 기능 1개만 계약코드를 갖고 나머지는 파생기획으로 둔다.

## 코드 이동 규칙

코드 이동은 기능 의미가 동일할 때만 허용한다.

예시:

```text
KINF-01 회원 본인 확인 → MBI-01 회원 본인 확인
```

이 경우 다음을 같이 확인한다.

- 0508 명칭과 신규 명칭이 실질적으로 같은가
- 하위 기능 구조가 유지되는가
- 계약코드 잔금 기준이 바뀌지 않는가
- 이전 코드 자리에 다른 기능을 넣지 않았는가

이전 코드 자리에 새 기능을 넣어야 하면 기존 번호를 재사용하지 않고 새 번호를 발급한다.

## 금지 사례

```text
0508:
IoT-01 = 키오스크 설정

잘못된 0518 방식:
IoT-01 = 통합 출석 관리

올바른 방식:
IoT-01 = 키오스크 설정 유지
IoT-07 = 통합 출석 관리 신규 발급
```

```text
0508:
IoT-02 = IoT 출입 관리

잘못된 0518 방식:
IoT-02 = 키오스크 설정 (통합 운영)

올바른 방식:
IoT-02 = IoT 출입 관리 유지
IoT-08 = 키오스크 설정 (통합 운영) 신규 발급
```

## 신규 기능코드 발급 체크리스트

- [ ] 같은 prefix의 0508 코드 목록을 확인했다.
- [ ] 같은 prefix의 현재 로컬 기능명세서 목록을 확인했다.
- [ ] 기존 코드와 기능 목적이 겹치지 않는다.
- [ ] 기존 계약코드 136개와 중복되지 않는다.
- [ ] 기존에 삭제/이동된 이력이 있는 번호를 재사용하지 않는다.
- [ ] 기능명세서 frontmatter에 `contract_codes` 또는 `contract_status`를 적었다.
- [ ] 화면설계서 `feature_codes`를 같은 코드로 연결했다.
- [ ] `pnpm docs:check`를 통과했다.
