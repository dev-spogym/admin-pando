Meeting Agenda

미팅에서 반드시 다뤄야 할 4대 안건

1. 현재 버전 설명

  • 완료된 범위는 자신 있게 설명
  • 남은 항목은 정책 확정 이슈인지, 작업 미완료인지 분리
  • 각 항목의 확정 시점과 개발 영향도까지 설명

2. 앞으로 바뀔 화면 관리

  • 이번 버전에서 바뀐 항목 요약
  • 추가 변경 가능성이 높은 영역 명시
  • 변경사항은 표 형태로 주기적으로 공유

3. 외주 개발사 작업 방식

  • 기능 리스트 축약본만 보지 않기
  • 상세 문서를 최소 1회 이상 직접 읽기
  • 이해한 내용을 다시 구조화해서 상호 확인

4. TC와 검수 기준

  • QA는 AI-only가 아니라 수동 + 자동화 병행
  • 주요 기능 기준 TC 초안을 미리 제시
  • 개발 완료 판단 기준을 TC와 검수 보고서로 통일
이번 미팅은 보고서 공유 자리가 아니라, 이후 개발과 검수 방식의 기준선을 합의하는 자리로 가져가야 합니다.

Ground Rules

외주 개발사에 명확히 전달할 기준

  • 기획문서는 AI에 던져보는 참고자료가 아니라, 사람이 먼저 읽고 해석해야 하는 기준 문서입니다.
  • 기능 리스트 축약본만으로 개발하지 않고, 원문과 상세 문서를 기준으로 해석해야 합니다.
  • 해석이 애매한 항목은 자체 추정으로 밀어붙이지 말고, 질의 후 확정된 기준으로 구현해야 합니다.
  • 변경사항은 수시로 발생할 수 있으므로, 누가 언제 어떤 방식으로 반영할지 운영 규칙이 필요합니다.
  • 개발 완료는 “구현했다고 주장하는 상태”가 아니라, TC 기준 검수 보고서까지 제출된 상태로 봅니다.
Questions

변경 반영 체계

  • 변경사항 공유 주기는 어떻게 잡을지
  • 반영 기준 버전은 누가 고정할지
  • 긴급 변경 발생 시 승인 루트는 무엇인지

문서 검토 책임자

  • 기획문서를 실제로 읽고 승인하는 사람이 누구인지
  • AI 활용은 어디까지이고 최종 판단자는 누구인지
  • 오해 발생 시 확인 창구는 누구인지

QA / TC 제출 체계

  • TC는 누가 작성하고 언제 제출하는지
  • 검수 보고서는 어떤 형식으로 받을지
  • 자동화와 수동 검수 비율은 어떻게 가져갈지

일정과 책임

  • 현재 일정상 병목이 생길 수 있는 부분은 무엇인지
  • 누가 어떤 범위를 오너십 있게 가져갈지
  • 추후 이슈 발생 시 판단 기준 문서는 무엇인지
