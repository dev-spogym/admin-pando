## 2. 화면 개요와 목적

회원 수정 페이지는 이미 등록된 회원의 인적사항·관리정보·추가정보를 변경하는 화면입니다. 회원 등록(SCR-M002)과 같은 컴포넌트·같은 2단계 구조를 재사용하되, 기존 회원 데이터가 모든 입력란에 미리 채워진 상태로 시작합니다. 운영자가 수정한 필드만 dirty 마크가 붙어 식별되며, 저장 시에는 변경된 필드만 PATCH 요청으로 전송됩니다. 모든 변경은 SCR-097 감사 로그에 변경 전/후 값과 함께 기록됩니다.

이 화면이 다루는 가장 흔한 시나리오는 회원의 연락처가 바뀌었을 때입니다. 회원이 번호를 바꿔서 알려오면 운영자는 회원 상세에서 "수정"을 눌러 이 화면에 들어와 연락처를 새 번호로 바꾸고 중복 확인을 다시 거친 다음 저장합니다. 두 번째로 흔한 케이스는 주소 변경(이사·이직)과 운동 목적·메모 갱신(상담 결과 반영)입니다. 회원 정보 자체가 잘못 입력되었던 경우를 정정하는 케이스도 자주 발생합니다.

회원 등록과 다른 점은 세 가지입니다. 첫째, 단계 잠금이 없어 Step 1과 Step 2를 자유롭게 오갈 수 있습니다. 둘째, 연락처가 변경되지 않으면 중복 확인이 필요 없고, 변경된 경우에만 중복 확인을 다시 거쳐야 합니다. 셋째, 초기화 버튼은 빈 폼이 아니라 원본 데이터로 되돌리는 동작입니다. 또한 branchId(소속 지점) 직접 변경은 차단되며, 지점 변경이 필요한 경우 SCR-M005 회원 이관 화면을 사용해야 합니다.

## 3. 진입 경로와 인접 화면

회원 수정 페이지로 들어오는 일반적인 경로는 회원 상세(SCR-M004) 헤더의 "수정" 버튼입니다. URL은 `/members/edit`로 전환되며, 이 시점에 회원 ID로 회원 데이터를 GET 호출해 폼에 자동 채움합니다. 두 번째 경로는 회원 목록(SCR-M001)의 행별 메뉴에서 "수정" 항목을 선택하는 것이고, 세 번째 경로는 본사 통합 모드에서 본사 권한자가 타 지점 회원을 검색해 수정할 때입니다.

이 화면을 빠져나가는 인접 화면으로는 저장 성공 후 자동으로 돌아가는 회원 상세(SCR-M004), 취소 시 호출 직전 화면(회원 상세 또는 회원 목록), 연락처 변경 시 호출되는 전화번호 중복 안내 DLG-M006이 있습니다. 모든 변경은 감사 로그(SCR-097)에 기록되어, 사후에 누가 어떤 필드를 언제 어떻게 바꿨는지 추적할 수 있습니다.

## 4. 레이아웃과 UI 구성

레이아웃은 회원 등록(SCR-M002)과 거의 동일합니다. 가장 위에 페이지 헤더("회원 수정"이라는 타이틀과 회원명·회원번호 배지)가 있고, 그 아래 2단계 진행 표시기, 프로필 사진 영역, Step 1 본문, Step 2 본문, 그리고 하단 고정 액션 바가 차례로 배치됩니다.

회원 등록과 시각적으로 가장 다른 부분은 화면 진입 직후 로딩 상태입니다. 회원 ID로 데이터를 GET 호출하는 동안 모든 입력란에 스켈레톤이 표시되고, 응답이 돌아온 직후 입력란에 기존 값이 채워지면서 스켈레톤이 사라집니다. 그 다음에는 회원 등록과 같은 레이아웃이지만 모든 입력란에 값이 미리 채워진 상태가 됩니다.

수정된 필드에는 작은 dirty 표시(라벨 옆 노랑 점)가 붙어 운영자가 어떤 필드를 바꿨는지 한눈에 알 수 있습니다. 헤더에는 작은 안내 배너가 있어 "변경된 항목만 저장됩니다"라는 문구가 표시되며, 변경이 한 건도 없으면 저장 버튼이 비활성화된 채로 유지됩니다.

진행 표시기는 회원 등록과 달리 단계 잠금이 없어, Step 1과 Step 2 둘 다 처음부터 클릭으로 자유롭게 이동할 수 있습니다. 프로필 사진 영역은 기존 사진이 미리 표시되어 있고 클릭하면 새 사진으로 교체할 수 있습니다. 사진을 제거하면 이니셜 아바타로 되돌아갑니다.

귀속 변경 이력 안내가 Step 1 관리 정보 그룹 상단에 추가로 표시됩니다. "소속지점·기본 이용지점·담당자·기본 귀속 정보를 수정하면 변경 전/후 값과 사유가 히스토리 로그에 남습니다"라는 안내 배너입니다. 소속지점(branchId)은 본 화면에서 직접 변경할 수 없으며, 변경 시도하면 회원 이관(SCR-M005)으로 안내하는 모달이 뜹니다.

하단 액션 바에서 Step 1은 "취소 / 다음", Step 2는 "이전 / 저장"입니다. 초기화 버튼은 헤더 우측에 있으며, 누르면 입력값이 원본 데이터로 되돌아갑니다(빈 폼이 아닙니다).

## 5. 단계별 동작과 화면 흐름

화면 진입 시 회원 ID로 `GET /api/members/:id`를 호출해 회원 데이터를 폼에 자동 채움합니다. 응답에는 회원의 모든 필드와 함께 `version` 컬럼이 포함되어 있어, 저장 시 optimistic lock 검증에 사용됩니다. 다른 운영자가 동시에 같은 회원을 수정해 version이 바뀌면 후행 저장은 409 Conflict로 거부됩니다.

Step 1에서는 자동 채움된 값 위에서 운영자가 필요한 필드만 수정합니다. 연락처 필드를 건드리면 옆의 "중복 확인" 버튼이 활성화되고, 새 번호가 입력되면 다시 중복 확인을 거쳐야 합니다. 기존 연락처와 동일하게 다시 입력한 경우(예: 실수로 지웠다가 같은 값으로 복원)는 중복 확인이 불필요하지만 UI는 안전하게 중복 확인을 요구합니다.

연락처가 새 번호로 변경되면 SMS·카카오 인증 토큰과 패스워드 리셋 토큰이 자동 무효화됩니다. 회원이 새 번호로 다시 인증해야 모바일 앱 로그인이 정상 동작하며, 이 정책은 인증 우회 사고를 막기 위한 것입니다.

소속지점(branchId) 드롭다운은 비활성화된 상태로 표시되고, 클릭 시 "지점 변경은 회원 이관 화면을 통해 가능합니다"라는 안내 모달이 뜨면서 SCR-M005로 이동할 수 있는 링크가 제공됩니다. 일반 매니저는 회원구분(일반↔법인) 변경이 불가능하며, 회원구분 라디오가 readonly 상태로 표시됩니다. 슈퍼관리자만 회원구분을 변경할 수 있고, 변경 시 법인 회사명 자동 비움 같은 부작용이 사전 경고와 함께 진행됩니다.

Step 2도 자동 채움된 값 위에서 수정합니다. 주소를 다시 검색하려면 주소 검색 버튼으로 DLG-M027을 호출합니다. 메모를 수정하면 새 본문이 그대로 저장되며, 본문 diff가 감사 로그에 기록됩니다.

"저장"을 누르면 dirty 마크가 붙은 필드만 모아 `PATCH /api/members/:id`로 전송합니다. 요청 본문에는 변경된 필드와 함께 `version`이 포함되며, 백엔드는 version 일치를 검증한 뒤 변경을 반영합니다. 성공 시 회원 상세로 돌아가면서 "N개 항목이 수정되었어요"라는 토스트가 표시됩니다.

광고 동의 변경은 한 방향으로만 가능합니다. 운영자가 동의 부여는 할 수 있지만 동의 철회는 회원 본인이 모바일 앱에서만 할 수 있다는 안내가 체크박스 아래 표시되고, 운영자가 체크 해제를 시도하면 안내가 떠 차단됩니다(전자문서법).

출석번호는 한번 발급되면 변경할 수 없도록 readonly로 표시됩니다. 변경이 필요한 예외 케이스(중복·실수)는 슈퍼관리자만 사유 입력 후 변경할 수 있고, 일반 매니저·스태프 화면에서는 출석번호 입력란이 readonly로 잠겨 있습니다.

## 6. 버튼·아이콘·링크 액션 전체 정의

프로필 사진 영역은 클릭으로 새 사진 업로드, 작은 휴지통 아이콘으로 제거가 가능합니다. EXIF GPS 자동 제거 정책이 동일하게 적용됩니다.

연락처 옆의 "중복 확인" 버튼은 연락처가 변경된 경우에만 활성화됩니다. 변경되지 않았다면 회색 비활성 상태로 유지되며 "이미 확인된 번호" 안내가 옆에 표시됩니다. 새 번호로 변경되면 활성화되고, 누르면 백엔드를 호출해 중복 여부를 확인합니다.

회원구분 라디오는 슈퍼관리자에게만 활성화되고 그 외 권한자에게는 readonly로 표시됩니다. 법인 → 일반 또는 일반 → 법인으로 변경 시 회사명 자동 비움 안내가 짧게 표시됩니다.

주소 검색 버튼은 DLG-M027을 호출합니다. 광고 동의 체크박스는 부여만 가능하고 철회는 차단됩니다.

하단 액션 바의 "취소" 버튼은 dirty 필드가 하나라도 있으면 DLG-M007을 띄우고, 변경 없음 상태면 즉시 회원 상세로 돌아갑니다. "초기화" 버튼은 dirty 필드가 있을 때만 활성화되며, 누르면 DLG-M008이 뜨고 확인 시 모든 필드가 원본 데이터로 복원됩니다.

"이전 / 다음" 버튼은 두 단계를 자유롭게 오가게 하고, "저장" 버튼은 dirty 필드가 한 건 이상 있을 때만 활성화됩니다.

## 7. 호출되는 모달 동작

### 7-1. DLG-M006 전화번호 중복 안내 다이얼로그

회원 수정에서는 연락처를 새 번호로 변경한 뒤 중복 확인을 눌렀을 때 호출됩니다. 동작은 회원 등록과 동일하지만, "기존 회원으로 이동"을 선택하면 현재 수정 중인 회원이 아닌 중복 발견된 다른 회원의 상세로 이동합니다. 강제 등록 옵션은 회원 수정에서는 의미가 없으므로 노출되지 않습니다.

### 7-2. DLG-M007 작업 취소 확인 다이얼로그

dirty 필드가 한 건 이상 있는 상태에서 취소 버튼을 누르면 호출됩니다. "계속 작성"은 모달만 닫고, "취소 확인"은 변경 사항을 폐기하고 회원 상세로 돌아갑니다. dirty 필드가 없으면 모달 없이 즉시 회원 상세로 돌아갑니다.

### 7-3. DLG-M008 입력 폼 초기화 확인 다이얼로그

수정된 내용을 원본으로 되돌리기 전 호출됩니다. 회원 등록의 빈 폼 리셋과 달리, 회원 수정에서는 원본 데이터로 복원이 동작이며 모달 본문도 "수정 전 값으로 돌아갑니다"로 다르게 표시됩니다.

### 7-4. DLG-M027 주소 검색 다이얼로그

기존 주소를 새 주소로 바꿀 때 호출됩니다. 동작은 회원 등록과 동일합니다.

## 8. 토스트와 확인 팝업과 알럿

저장 성공 시 회원 상세로 돌아가면서 "N개 항목이 수정되었어요" 토스트가 표시됩니다. N은 dirty 필드 개수이며 0이면 저장 버튼 자체가 비활성이므로 발생하지 않습니다. 변경된 필드가 연락처를 포함하면 토스트 옆에 "기존 인증 정보가 초기화되었습니다" 부가 안내가 따라옵니다.

동시 편집 충돌(409)이 발생하면 "다른 운영자가 동시에 이 회원을 편집했어요"라는 모달이 뜨고, "새로고침 후 재시도" 버튼이 제공됩니다. 누르면 페이지가 새로고침되어 최신 데이터가 로드됩니다.

회원이 다른 운영자에 의해 탈퇴 처리된 상태에서 저장을 시도하면 "이미 탈퇴된 회원입니다" 모달이 뜨고 회원 상세 또는 목록으로 이동할 수 있는 링크가 제공됩니다.

회원 정보 조회 실패(404 또는 권한 부족)는 화면 본문 자체가 사라지면서 "회원을 찾을 수 없습니다" 또는 "이 회원에 접근할 권한이 없습니다" 메시지와 함께 목록으로 이동 버튼이 표시됩니다.

광고 동의 체크 해제 시도 시 "동의 철회는 회원 본인 앱에서만 가능합니다"라는 안내가 토스트로 표시되고 체크 상태는 유지됩니다. branchId 변경 시도 시 "지점 변경은 회원 이관 화면을 통해 가능합니다"라는 모달이 뜨고 SCR-M005로 이동할 수 있는 링크가 제공됩니다.

## 9. 데이터 흐름과 외부 연동

화면 진입 시 `GET /api/members/:id`로 회원 데이터를 가져옵니다. 응답에는 모든 필드 값과 `version` 컬럼, 그리고 권한 검증 결과(`canEdit`, `canChangeRole`)가 포함됩니다.

연락처가 변경된 경우 `POST /api/members/check-phone`을 호출하며, 본인 회원 ID는 검색에서 제외됩니다(자기 자신과의 중복 검출 방지). 응답 형식은 회원 등록과 동일합니다.

저장은 `PATCH /api/members/:id`를 호출합니다. 요청 본문에는 dirty 필드와 `version`이 포함되며, 백엔드는 version 일치를 검증한 뒤 변경을 적용합니다. 연락처가 변경된 경우 `POST /api/members/:id/restore-token-revoke`가 함께 호출되어 SMS·카카오 인증 토큰과 패스워드 리셋 토큰이 무효화됩니다.

저장이 완료되면 SCR-097 감사 로그에 변경된 필드별 before/after JSON이 INSERT됩니다. 메모 변경은 본문 diff 형태로 기록되어 어떤 부분이 추가·삭제·수정되었는지 사후 추적이 가능합니다.

연락처 변경 시 자동화 체인이 트리거됩니다. 기존 인증 토큰 무효화, 모바일 앱에 새 번호로 재인증 SMS 발송, 마케팅 CRM의 알림톡 발송 대상 갱신이 단일 트랜잭션 내에서 처리됩니다. 회원 등급(MBR-EXT-03)이나 세그먼트(MBR-EXT-04) 라벨은 회원 수정으로 직접 변경되지 않지만, 광고 동의 변경은 카카오 알림톡 발송 대상에 영향을 줍니다.

화면에서 호출하는 주요 API: 회원 데이터 조회 `GET /api/members/:id`, 연락처 중복 확인 `POST /api/members/check-phone`, 회원 정보 수정 `PATCH /api/members/:id`, 인증 토큰 무효화 `POST /api/members/:id/restore-token-revoke`, 이미지 업로드 `POST /api/upload/profile-image`, 주소 검색 `GET /api/address/search`.

## 10. 화면 상태와 예외 처리

이 화면이 가질 수 있는 상태들을 정의합니다.

데이터 불러오는 중 상태에서는 모든 입력란에 스켈레톤이 표시됩니다. 초기값 채워짐 상태는 GET 응답이 도착해 모든 필드에 기존 값이 채워진 직후이며 dirty 필드는 0개입니다. 수정 중 상태는 한 필드 이상이 dirty인 상태로, 저장 버튼이 활성화되고 dirty 필드 옆에 노랑 점이 표시됩니다.

귀속 정보 수정 중 상태는 소속지점 외의 귀속 관련 필드(기본 이용지점·담당자·기본 매출 귀속·기본 인센티브 귀속자)가 수정된 상태로, 저장 시 변경 사유를 함께 묻는 모달이 추가로 표시될 수 있습니다(정책 옵션).

저장 중 상태에서는 액션 바가 모두 비활성화되고 스피너가 표시됩니다. 불러오기 실패 상태는 GET 호출이 실패했거나 회원이 존재하지 않거나 권한이 없는 경우로, 본문이 사라지고 "회원을 찾을 수 없습니다" 또는 "권한이 없습니다" 메시지가 표시됩니다.

예외 케이스별 처리는 다음과 같습니다. 회원 ID가 잘못된 URL로 진입하면 404 응답을 받고 본문 자체가 에러 메시지로 대체됩니다. 회원이 다른 운영자에 의해 탈퇴된 상태로 저장 시도하면 409 또는 422 응답을 받고 "이미 탈퇴된 회원입니다" 모달이 표시됩니다. 동시 수정 충돌(version 불일치)은 409 응답을 받고 새로고침 안내가 표시됩니다.

연락처 형식 오류, 이름 형식 오류, 메모 주민번호 패턴 검출, 이미지 5MB 초과 등 회원 등록과 동일한 검증 정책이 적용됩니다. 만 14세 미만 + 법정대리인 미동의 케이스는 수정 흐름에서도 동일하게 차단됩니다.

권한 부족(403)으로 저장 실패 시 "권한이 없어요" 토스트가 표시되고 입력값은 유지된 채 저장이 중단됩니다.

## 11. 권한별 처리

슈퍼관리자(superAdmin)와 본사 최고관리자(primary)는 모든 필드를 수정할 수 있습니다. 회원구분 변경, 출석번호 변경, 본사 통합 모드에서 타 지점 회원 수정이 모두 가능합니다. 단 branchId 직접 변경은 회원 이관 화면을 통해서만 가능합니다.

Owner(지점장)·매니저(manager)는 자기 지점 회원의 대부분 필드를 수정할 수 있지만 회원구분(일반↔법인) 변경은 차단됩니다. 출석번호 변경도 불가능합니다.

스태프(staff)는 자기 지점 회원의 기본 인적사항·관리정보·추가 연락정보·메모를 수정할 수 있지만, 회원구분과 출석번호는 readonly입니다.

FC(fc)는 자기 담당 회원의 메모와 운동 목적만 수정할 수 있고, 그 외 필드는 readonly입니다. 진입은 가능하지만 대부분 입력란이 잠겨 있습니다.

트레이너(trainer)·프런트(front)·readonly는 이 화면에 진입할 수 없습니다. 직접 URL 진입 시 접근 제한 알럿 후 대시보드로 자동 이동됩니다.

권한별 readonly/숨김 처리는 UI와 백엔드 양쪽에서 일관되게 적용되며, 권한이 부족한 사용자가 직접 API를 호출해도 백엔드가 403으로 거부합니다. 모든 권한 차단 이벤트는 감사 로그에 기록됩니다.

## 14. 핵심 디자인 요청사항

수정 화면이 운영자에게 잘 작동하려면 다음 디자인 원칙이 시각적으로 명확해야 합니다.

dirty 마크는 작은 노랑 점이나 라벨 색상 변화로 표현되어, 어떤 필드를 수정했는지 한눈에 보여야 합니다. 저장 버튼은 dirty 필드가 0개일 때 회색 비활성, 1개 이상이면 강조 색상으로 활성되어 운영자가 저장 가능 여부를 즉시 인지할 수 있어야 합니다.

readonly 필드는 단순한 비활성화보다 명확한 시각적 단서로 표현해야 합니다. 입력란 배경을 약간 흐리게 처리하고 우측에 작은 자물쇠 아이콘을 붙여, 권한 또는 정책으로 수정이 차단되어 있음을 알 수 있게 합니다. 자물쇠 호버 시 차단 사유(예: "지점 변경은 이관 화면에서 가능", "회원구분 변경은 슈퍼관리자만 가능")가 툴팁으로 표시됩니다.

연락처 변경 시 "이미 확인된 번호" → "변경됨, 재확인 필요" → "확인 완료(초록 체크)"의 3단계 상태 전환이 색상과 아이콘으로 명확히 구분되어야 합니다.

화면 진입 직후의 로딩 스켈레톤은 실제 폼 레이아웃과 동일한 형태로 표시되어 사용자가 어디에 무엇이 들어올지 예측할 수 있게 합니다.

저장 직후 "N개 항목이 수정되었어요" 토스트는 N이 1보다 클 때는 강조 톤으로, 1일 때는 일반 톤으로 표시해 변경 규모를 직관적으로 전달합니다.

## 15. 운영 정책 (이 화면에 연결된 부분)

회원 수정에 특화된 정책을 풀어 적습니다. 회원 등록과 공통된 정책(이름 형식·만 14세·메모 민감정보·EXIF GPS·중복 확인 30초 등)은 SCR-M002 문서에서 풀어 적었으며 여기서는 수정 흐름의 고유 정책에 집중합니다.

변경된 필드만 PATCH로 전송하는 정책은 두 가지 이유로 존재합니다. 첫째, 다른 운영자가 동시에 다른 필드를 수정해도 충돌이 발생하지 않습니다(필드 단위 충돌만 발생). 둘째, 감사 로그가 깔끔하게 남아 사후 추적이 쉽습니다.

optimistic lock(`version` 컬럼) 정책은 동시 수정 충돌을 막기 위한 것입니다. 두 운영자가 동시에 같은 회원을 수정해 저장하면 후행 요청은 거부되고, 후행 운영자는 새로고침 후 다시 수정해야 합니다. 이 정책 덕분에 한 운영자의 변경이 다른 운영자의 변경을 무심코 덮어쓰는 사고가 차단됩니다.

연락처 변경 시 SMS·카카오 인증 토큰과 패스워드 리셋 토큰을 무효화하는 정책은 인증 우회 사고를 막기 위한 것입니다. 만약 무효화하지 않으면, 회원의 이전 번호로 발급된 토큰이 살아 있는 상태에서 새 번호의 회원이 다른 사람일 경우 인증 정보가 의도치 않게 노출될 수 있습니다.

branchId 직접 변경 차단 정책은 데이터 일관성을 위한 것입니다. 이 화면에서 소속지점만 바꾸면 결제·이용권·출석 이력의 귀속이 깨지므로, 지점 변경은 SCR-M005 회원 이관 화면을 통해 6종 체크리스트(미수금·락커·홀딩·PT 잔여·쿠폰·마일리지) 검증과 함께 진행되어야 합니다.

광고 동의 철회 차단 정책(부여는 가능, 철회는 회원 본인 앱에서만)은 전자문서법에 따른 결과입니다. 운영자가 동의 철회까지 할 수 있게 하면 마케팅 동의의 법적 효력이 약해집니다.

출석번호 변경 차단 정책(슈퍼관리자만 사유 입력 후 가능)은 출석 이력 추적성을 위한 것입니다. 한번 발급된 출석번호는 그 회원의 출석 기록과 결합되어 있으며, 임의 변경은 이력 정합성을 깨뜨립니다.

권한별 수정 가능 필드 제한(매니저는 회원구분 변경 불가, FC/트레이너는 메모·운동목적 외 수정 불가)은 운영 실수의 영향을 최소화하기 위한 RBAC 세부 정책입니다.

회원 기본 귀속 변경 시 히스토리 로그에 변경 전/후 값과 사유를 남기는 정책은 운영 결정의 추적성을 위한 것입니다. 누가 언제 어떤 이유로 회원의 담당자·기본 이용지점·기본 매출 귀속을 바꿨는지 사후에 확인할 수 있어야 운영 결정의 책임이 명확해집니다.

수정 결과를 즉시 감사 로그(SCR-097)에 기록하는 정책은 5초 안에 INSERT가 보장되어야 하며, 변경된 필드별 before/after JSON이 actor_id·timestamp와 함께 저장됩니다. 메모는 본문 diff로 저장되어 어느 문장이 추가·삭제·수정되었는지 알 수 있습니다.

이상의 정책들은 회원 수정이 운영 현장에서 일으킬 수 있는 사고를 최소화하기 위한 안전장치들이며, 별도 문서를 보지 않고도 이 한 장으로 구현·운영이 가능하도록 풀어 적었습니다.
