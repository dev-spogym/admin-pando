## 2. 발견된 불일치 및 보정 내역

### A. 카테고리 간 불일치

#### A-1. 권한 역할 체계 — 7표준 vs 9확장 표기 정합성 (가장 큰 불일치)

| 출처 | 정의된 역할 수 | 역할 키워드 |
| --- | --- | --- |
| 운영기획서 §3 (정본) | **7개 표준 역할** | `superAdmin / primary / owner / manager / fc / staff / readonly` |
| 운영기획서 §4 운영 원칙 | `front`는 표준 역할 아님 (staff에 포함), `trainer`는 관리자 웹 기본 역할 아님 (앱·수업 관점) | — |
| 통합 ID 대응표 L81 | 7개 표준 역할 (위와 동일) | `superAdmin/primary/owner/manager/fc/staff/readonly` |
| 본 도메인 D01 README 전체 | **9개 역할** (7 + trainer + front) 일관 노출 | `superAdmin / primary / owner / manager / fc / staff / front / trainer / readonly` |

**판단**: 운영기획서 §4 운영 원칙(`front`는 staff에 포함, `trainer`는 앱·수업 관점)을 정본으로 보면, 본 도메인 README의 9개 노출은 "표준 7개 + 부가 노출 2개(staff에 포함되는 front, 앱 연동 관점의 trainer)"로 해석된다. 단, 어떤 README도 이 매핑("front=staff 내포", "trainer=비표준 부가")을 명시적으로 풀어 적지 않아, 운영자가 9개를 동등한 권한 분기로 오해할 위험이 있다.

**보정 내역** (직접 수정):
- `SCR-102 사이드바 네비게이션/README.md` §14 첫 단락 — 이미 표준 7역할 정의(L291)를 갖고 있으나, 9개 노출과 7개 표준의 매핑이 한 문장으로 짧게만 처리되어 있어 보강함. `staff가 front를 포함하는 단일 표준 역할`, `trainer는 관리자 웹 기본 표준 역할이 아니라 앱·수업 운영 관점의 역할`이라는 운영기획서 §4 원칙을 인용 형태로 명시.
- 그 외 15개 README는 같은 9개 역할을 같은 키워드(`superAdmin·primary·owner·manager·fc·staff·front·trainer·readonly`)로 일관 사용하고 있어 본 검수에서 추가 직접 수정 없이 SCR-102가 단일 정의 위치 역할을 한다는 점을 명시.

#### A-6. SCR-101 표준 진입자 분기 — 일관성 미세 확인

SCR-100 §11 "권한별 라우팅"과 SCR-101 §3·§12·SCR-102 §5 "역할별 라우팅"을 교차 확인:

| 역할 | SCR-100 §11 진입 화면 | SCR-101 §3·§12 진입 여부 | SCR-102 §5 대시보드 메뉴 라우팅 |
| --- | --- | --- | --- |
| superAdmin | 슈퍼 대시보드 | SCR-101 또는 SCR-090 | SCR-101 또는 SCR-090 (본사 정책) |
| primary | 본사 대시보드 (또는 지점 대시보드 통합) | SCR-101 또는 SCR-090 | SCR-101 또는 SCR-090 |
| owner | SCR-090 DASH-01 (지점 대시보드) | SCR-101 — 본 화면 진입 | SCR-101 또는 SCR-090 |
| manager | 지점 대시보드 | SCR-101 — 본 화면 진입 | SCR-101 또는 SCR-090 |
| fc | 수업 캘린더 또는 지점 대시보드 | SCR-101 — 본 화면 진입 | SCR-101 |
| staff/front | 출석 관리 | SCR-101 진입 안 함 — Z2 라우팅 | SCR-102 §5에서 staff·front는 대시보드 메뉴가 출석 관리로 라우팅 |
| trainer | 수업 캘린더 | SCR-101 진입 안 함 — Z1 라우팅 | SCR-102 §5에서 trainer는 대시보드 메뉴가 수업 캘린더로 라우팅 |
| readonly | 급여 명세서 또는 운영 정책 지정 화면 | SCR-101 — 전체 위젯 조회만 (SCR-101 §11) | SCR-102 §5는 명시 없음 — 본사 정책에 따른 읽기 전용 기본 화면 |

**판단**: 분기 자체는 일관하지만, owner/manager/fc는 SCR-100에서 "지점 대시보드(SCR-090)" 진입을, SCR-101에서는 "본 화면 진입"으로 적혀 정합도가 미세하게 달라 보일 수 있다. 그러나 SCR-101 §2 첫 단락에서 "사이드바 상단의 대시보드 메뉴를 누르면 본 화면으로 돌아올 수 있어 운영의 허브 역할"이라는 점, SCR-101 §11에서 "owner·manager·fc 모두 본 화면의 모든 위젯을 사용할 수 있다"고 명시한 점을 종합하면, SCR-090은 별개의 본사 통합 KPI 화면이고 SCR-101은 역할별 통합 진입 뷰라는 분담이 일관되게 유지된다. 보정 불요.

보정 불요.

#### B-5. 사이드바 권한별 메뉴 표시 룰 — 운영기획서 §10·§11 정합 확인

운영기획서 §10 핵심 기능별 최소 운영 권한 (정본):
- 리드 등록/수정: fc 이상
- 회원 등록/수정: staff 이상
- 회원 상태 일괄 변경: manager 이상
- 상품 배포: primary 이상
- 결제 승인/환불: manager 이상
- 지점 이관 승인: manager 이상
- 자동화 정책 생성: primary 이상
- 자동화 정책 적용: owner 또는 manager
- 권한 템플릿 관리: superAdmin 또는 primary
- 본사 통합 KPI 조회: primary 이상
- 지점 KPI 조회: owner 이상
- 개인 KPI 조회: manager 이상

SCR-102 §5·§14 정합 확인:

| 메뉴 | SCR-102 §5 노출 권한 | 운영기획서 §10 최소 권한 정합 |
| --- | --- | --- |
| 대시보드 | 모든 인증 사용자 | — (조회 공통) |
| KPI 센터 | owner·primary·superAdmin | 지점 KPI = owner 이상 ✓ |
| 회원관리 | 모든 인증 사용자 | 회원 등록 = staff 이상 (조회는 공통) ✓ |
| 매출관리 | trainer 제외, 슈퍼/primary/owner/manager/fc | 결제 승인·환불 = manager 이상 ✓ (fc 조회만 일관) |
| 상품관리 | superAdmin·primary·owner·manager | 상품 배포 = primary 이상 ✓ (manager 이하는 조회) |
| 직원관리 | superAdmin·primary·owner (manager 일부) | — (운영기획서에 명시 없음) |
| 본사관리 | superAdmin·primary만 | 본사 통합 KPI = primary 이상 ✓ |
| 설정 | superAdmin·primary·owner (manager 일부) | — |
| 마케팅 | 슈퍼/primary/owner/manager/fc | 리드 등록 = fc 이상 ✓ |

운영기획서 §10 권한 기준이 SCR-102 §5 메뉴 노출 룰에 일관 반영. 운영기획서 §11 "화면 노출 기준" 5개 원칙(메뉴 숨김 vs 읽기전용 / 위험 기능 사전 제한 / readonly 다운로드 별도 / 본사·지점 메뉴 분리 / 권한 수준 상단 표시)도 SCR-102 §14에 자기완결로 풀어 적힘.

보정 불요.

## 4. SCR-102 §14 보강 텍스트

(아래는 SCR-102 §14 "관리자 웹 표준 역할 정책" 단락을 보강해 9역할 노출과 7표준 정본의 매핑을 명시한 텍스트입니다.)

```markdown
관리자 웹 표준 역할 정책은 운영기획서 §3·§4를 정본으로 하여 다음 7개를 기준으로 한다.
superAdmin(전사 최고 권한), primary(본사 운영 총괄), owner(지점 최고 책임자),
manager(지점 운영 관리자), fc(상담·영업 담당), staff(현장 운영 담당), readonly(조회 전용).
본 시스템에서 front는 별도 표준 역할로 두지 않고 staff에 포함하며, trainer는 관리자 웹의
기본 역할이 아니라 앱·수업 운영 관점의 역할로 본다. 사이드바의 메뉴 세트는 이 7개 표준
역할을 기본 축으로 계산되며, front는 staff와 동일한 메뉴 세트를, trainer는 관리자 웹 진입이
필요한 운영 환경에서만 좁은 메뉴 세트로 노출된다. 본 도메인 D01의 모든 README가 9개 키워드
(superAdmin·primary·owner·manager·fc·staff·front·trainer·readonly)를 일관 사용하는 이유는
front·trainer가 운영 현장에서 별도 매핑되는 부가 역할이기 때문이며, 권한 분기 자체는 7개
표준 역할을 기준으로 한다.
```

본 검수에서는 SCR-102 README L291 부근(§14 첫 단락)의 기존 단락이 이미 7표준 정의 + front 매핑 + trainer 매핑을 포함하고 있어, 추가 단락을 강제로 삽입하기보다 **현재 기술 수준이 운영기획서 §3·§4와 정합한지를 확인**하는 데 그쳤다. SCR-102 §14 L291의 현재 문장:

> 관리자 웹 표준 역할 정책은 다음 7개를 기준으로 합니다. superAdmin(전사 최고 권한), primary(본사 운영 총괄), owner(지점 최고 책임자), manager(지점 운영 관리자), fc(상담·영업 담당), staff(현장 운영 담당), readonly(조회 전용). 본 시스템에서 front는 별도 표준 역할로 두지 않고 staff에 포함하며, trainer는 관리자 웹의 기본 역할이 아니라 앱·수업 운영 관점의 역할로 봅니다. 사이드바의 메뉴 세트는 이 7개 표준 역할을 기본 축으로 계산됩니다.

→ 운영기획서 §3·§4와 100% 정합. **추가 직접 수정 없음**. 본 검수 결과 문서가 단일 정의 위치(SCR-102 §14)를 명시하는 것으로 갈음.
