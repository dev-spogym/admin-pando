# docs-domain — 화면 단위 자기완결형 요구사항정의서

## 이 폴더의 목적

이 폴더는 FitGenie 관리자(admin) 시스템을 화면 단위로 분해해서, 각 화면(SCR)과 다이얼로그(DLG)마다 폴더 하나씩을 두고 그 안에 한 장의 `README.md`로 그 화면에 대한 모든 것을 자기완결적으로 풀어 쓴 문서 모음입니다. 개발자는 어떤 화면을 구현할 때 다른 문서를 찾아다닐 필요 없이 그 화면의 폴더만 열면 메타 정보·UI 구성·탭·버튼·모달·팝업·토스트·데이터 흐름·상태·예외·권한별 처리·운영 정책까지 전부 한 자리에서 확인할 수 있도록 작성합니다.

## 작성 원칙

이 폴더의 모든 문서는 다음 원칙을 따릅니다.

첫째, 한 화면(또는 한 다이얼로그)은 한 폴더이며, 폴더 안에는 단 하나의 `README.md`만 둡니다. 화면을 여러 문서로 쪼개지 않으며, 섹션 분리도 한 문서 내부에서 해결합니다.

둘째, 외부 문서로의 참조나 경로 표기를 쓰지 않습니다. "○○ 문서 참고", "○○ 경로 참고" 같은 표현 대신, 필요한 내용은 그 폴더 안에서 전부 직접 풀어 씁니다. 다른 화면에서 호출되는 모달도 호출하는 화면 폴더마다 그 화면 맥락에서 자기완결적으로 풀어 쓰며, 다이얼로그 자체에도 별도 폴더와 문서가 존재합니다.

셋째, 톤은 요구사항정의서 스타일의 문장 풀이형을 기본으로 합니다. 표와 bullet은 보조 도구로만 사용하며, 메인 서술은 문장으로 풀어서 진행됩니다.

넷째, 메타 정보에 작성일과 화면 ID와 기능코드와 계약코드를 반드시 명시합니다. 기능코드 발급 규칙(같은 prefix의 다음 번호 사용, 기존 코드 의미 보존)과 계약코드 정합성(최초 계약 136개 코드의 정본 유지)을 그대로 따릅니다.

다섯째, 권한별 처리·탭 동작·버튼 동작·모달 동작·팝업 동작·토스트·운영 정책까지 빠짐없이 그 화면 폴더 안에 녹여 넣습니다. 운영 정책은 별도 파일로 분리하지 않고, 그 화면과 관련된 부분만 화면 문서 안에 풀어 씁니다.

여섯째, 백엔드 사양(API와 DB 스키마)은 화면이 호출하는 엔드포인트 정도만 적고 깊게 들어가지 않습니다.

일곱째, 메인 흐름과 에러 흐름을 Mermaid 다이어그램으로 직접 임베드해 보조합니다.

여덟째, 기획 카테고리(기능명세서·화면설계서·다이어그램·운영 문서) 간 불일치가 발견되면 일관된 값으로 통일해 작성합니다.

## 폴더 네이밍 규칙

도메인 폴더는 `D[번호] [한글]/` 형식입니다. 예를 들어 `D02 회원관리/`처럼 도메인 코드와 한글명을 공백으로 띄어 씁니다.

화면 폴더는 `SCR-[ID] [한글 화면명] 페이지/` 형식입니다. 예를 들어 `SCR-M001 회원목록 페이지/`처럼 화면 ID와 한글명과 "페이지" 접미사를 공백으로 띄어 씁니다.

다이얼로그 폴더는 `DLG-[ID] [한글 다이얼로그명] 다이얼로그/` 형식입니다. 예를 들어 `DLG-M001 상태변경 다이얼로그/`처럼 다이얼로그 ID와 한글명과 "다이얼로그" 접미사를 공백으로 띄어 씁니다.

폴더 안의 문서는 항상 `README.md` 한 장입니다.

## 문서 표준 섹션 (15개)

각 화면 폴더의 `README.md`는 다음 15개 섹션으로 구성됩니다.

1. 화면 메타 정보
2. 화면 개요와 목적
3. 진입 경로와 인접 화면
4. 레이아웃과 UI 구성
5. 탭 구성과 탭별 동작
6. 버튼·아이콘·링크 액션 전체 정의
7. 호출되는 모달 동작
8. 토스트와 확인 팝업과 알럿
9. 데이터 흐름과 외부 연동
10. 화면 상태와 예외 처리
11. 권한별 처리
12. 메인 흐름 (Mermaid)
13. 에러와 예외 흐름 (Mermaid)
14. 핵심 디자인 요청사항
15. 운영 정책 (이 화면에 연결된 부분)

다이얼로그 폴더는 위 구조를 다이얼로그 맥락에 맞게 압축한 형태(메타·목적·호출 트리거·UI 구성·필드·검증·확인/취소 후 동작·권한·예외·운영 정책)로 작성합니다.

## 도메인 개요

D01 공통 도메인은 로그인·대시보드·사이드바·글로벌 검색·알림 센터·프로필·비밀번호 재설정·에러 페이지·로그아웃·클라이언트 프리뷰처럼 모든 관리자 화면에 공통으로 적용되는 영역을 다룹니다. 세션 만료·로그아웃 확인·이탈 경고·삭제 확인·저장 확인 같은 범용 다이얼로그도 이 도메인에 속합니다.

D02 회원관리 도메인은 회원 목록·등록·수정·상세·이관·체성분·병합·가족·등급·세그먼트 같은 회원 원장과 관련된 모든 화면을 다룹니다. 회원 운영의 핵심 허브이며, 회원 상태 변경·홀딩·탈퇴·상담·메모 등 약 30개의 다이얼로그가 동작합니다.

D03 매출관리 도메인은 매출 현황·POS 판매·결제 처리·매출 통계·통계 관리·선수익금·환불·미수금·할부·세금계산서·매출 예측·결제 취소 부분 환불처럼 결제와 매출 관련 운영을 다룹니다.

D04 수업관리 도메인은 수업 캘린더·수업 관리·시간표 일괄 등록·그룹 수업 템플릿·그룹 수업 현황·강사 근무 현황·횟수 관리·페널티 관리·일정 요청 처리·운동 프로그램·유효 수업·대기열·수업 평가·QR 체크인·녹화·예약 목록을 다룹니다.

D05 상품관리 도메인은 상품 관리·등록 수정·상세 패널·할인 설정·카탈로그·비교·재고 관리·시즌 가격 관리를 다룹니다. 상품과 이용권의 운영 정책이 함께 녹아 들어갑니다.

D06 시설관리 도메인은 락커 관리·사물함 배정·밴드 카드(RFID)·운동 룸·골프 타석·운동복·장비 점검·소모품 재고·청소 스케줄·공간 자산을 다룹니다.

D07 직원관리 도메인은 직원 목록·등록 수정·퇴사 처리·근태 관리·급여 관리·급여 명세서를 다룹니다. 직원 역할과 권한이 이 도메인에서 시작됩니다.

D08 마케팅 도메인은 리드 관리·메시지 발송·자동 알림 설정·자동 알림 운영 현황·쿠폰 관리·마일리지 관리·전자 계약·캠페인 관리·리퍼럴 프로그램·SMS 카카오 발송·AB 테스트를 다룹니다. 자동 알림 13종 엔진의 운영이 이 도메인의 중심입니다.

D09 설정관리 도메인은 센터 설정·지점 자동화 적용·권한 설정·키오스크 설정·키오스크 IoT 설정·IoT 출입 관리·구독 결제·공지사항·출석 관리 설정·커스텀 역할·다국어·데이터 백업 복원을 다룹니다.

D10 본사관리 도메인은 본사 대시보드·슈퍼 대시보드·지점 관리·지점 성과 리포트·KPI 대시보드·KPI 프리뷰·온보딩 대시보드·감사 로그·오늘의 할 일·리포트 생성·자동화 정책 라이브러리·커스텀 대시보드 빌더·벤치마크 비교·예측 분석·NPS 설문을 다룹니다. 본사 권한자가 전 지점을 통합 운영하는 모든 화면이 이 도메인에 모입니다.

D11 통합운영 도메인은 통합 출석 관리·키오스크 설정·IoT 연동 관리·옷락커 운영·고정 물품 락커·체성분 통합·회원 건강 연동·키오스크 운영 현황을 다룹니다. 외부 디바이스와 IoT 인프라가 회원 운영에 연결되는 지점입니다.

## 사용 방법

이 폴더는 개발자가 화면을 구현할 때 처음 열어보는 정본 문서입니다. 사용 흐름은 다음과 같습니다.

먼저 어떤 화면을 구현할지 정하면, 그 화면이 속한 도메인 폴더(예: `D02 회원관리/`)로 이동합니다. 도메인 폴더의 `README.md`에서 화면 ID와 한 줄 설명을 확인하고, 해당 화면 폴더(예: `SCR-M001 회원목록 페이지/`)로 들어갑니다. 그 폴더의 `README.md` 한 장을 끝까지 읽으면 그 화면 구현에 필요한 모든 정보가 들어 있습니다.

다른 화면에서 호출되는 모달을 다룰 때는 두 가지 방법이 있습니다. 첫째, 호출하는 화면 폴더의 `README.md` 안에 그 모달이 그 화면 맥락에서 어떻게 동작하는지가 풀려 있습니다. 둘째, 그 다이얼로그 자체의 폴더(예: `DLG-M001 상태변경 다이얼로그/`)에 다이얼로그 단독 문서도 있습니다. 일반적으로 구현 단계에서는 호출 화면 폴더의 설명이 우선이며, 다이얼로그 단독 문서는 모달 자체의 재사용 패턴을 확인할 때 참고합니다.

운영 정책을 별도로 찾을 필요는 없습니다. 화면 문서의 마지막 섹션에 그 화면과 관련된 운영 정책(회원 상태 운영 정의·세그먼트 우선순위·자동화 배치 시점·PII 마스킹 정책·감사 로그 기록 기준·권한별 책임 분리 등)이 풀려 있습니다.

## 문서 갱신 원칙

코드가 바뀌면 화면 문서도 함께 바뀌어야 합니다. 정책이 바뀌면 그 정책이 녹아 있는 모든 화면 문서가 함께 갱신되어야 합니다. 문서와 코드와 정책은 항상 짝지어 진행되며, 어느 한쪽만 바뀌어 다른 쪽과 어긋난 상태로 남지 않게 합니다.

기능코드와 계약코드는 변경하지 않는 것이 원칙입니다. 명칭만 보강되는 경우에는 기존 코드를 유지하고, 기능 목적 자체가 바뀐 경우에는 기존 코드를 삭제하고 신규 코드를 발급합니다. 이 규칙은 계약 잔금 산정의 안정성을 위한 것이며, 화면 문서의 메타 정보가 코드 변경 이력을 그대로 반영해야 합니다.
