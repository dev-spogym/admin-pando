# docs-domain 검수·정합화 체크리스트

11개 도메인 deep-executor가 자율 작성한 문서가 모이면 이 체크리스트로 검수와 정합화를 진행합니다. 검수는 화면 단위와 도메인 단위, 그리고 전체 단위의 세 층위로 진행합니다.

## 1. 폴더와 파일 구조 검증

각 도메인 폴더 안의 모든 화면·다이얼로그 폴더가 누락 없이 생성되었는지 확인합니다. 도메인별 SCR 수와 DLG 수가 마스터 인덱스(`docs-domain/README.md`)의 카운트와 일치해야 합니다. 각 폴더 안에는 정확히 `README.md` 한 장만 존재해야 하며, 그 외 보조 파일은 허용하지 않습니다.

폴더명 규칙은 도메인이 `D[번호] [한글]/`, 화면이 `SCR-[ID] [한글] 페이지/`, 다이얼로그가 `DLG-[ID] [한글] 다이얼로그/` 형식이어야 합니다. 한글 사이의 공백 유무가 도메인별 에이전트마다 달라졌을 가능성이 있으므로, 폴더명 일관성 검사를 우선 수행합니다.

## 2. 문서 메타 정보 검증

각 화면 README.md의 첫 섹션이 메타 정보 표여야 하며, 다음 항목이 빠짐없이 명시되어야 합니다.

- 작성일 = 2026-05-22 (현재 시점 기준)
- 버전 (예: v1.0)
- 상태 (예: 최신 통합본 반영)
- 도메인 (예: D02 회원관리)
- 화면 ID 또는 다이얼로그 ID (정확한 코드)
- 화면명 또는 다이얼로그명
- 화면 유형 (허브 / 일반 / 다이얼로그)
- 라우트 URL (화면 한정)
- 플랫폼 (데스크톱 / 태블릿 / 모바일)
- 우선순위 (P0 / P1 / P2)
- 기능코드 (예: MBR-01)
- 계약코드 (있는 경우 모두, 없으면 contract_status 표기)
- Lv2 / Lv3 세분화 (해당되는 경우)
- 연계 화면
- 호출 다이얼로그

기능코드 발급 규칙과 계약코드 정합성 점검 결과를 그대로 따랐는지 확인합니다. 기존 코드 의미를 보존하고, 신규 코드는 같은 prefix의 다음 번호로 발급된 것이어야 합니다.

## 3. 15개 표준 섹션 누락 검증

각 화면 README.md에 다음 15개 섹션이 모두 존재하는지 확인합니다. 일부 다이얼로그는 압축형이라 14·15번이 짧을 수 있지만, 1~13번은 모든 문서에 있어야 합니다.

1. 화면 메타 정보
2. 화면 개요와 목적
3. 진입 경로와 인접 화면
4. 레이아웃과 UI 구성
5. 탭 구성과 탭별 동작
6. 버튼·아이콘·링크 액션 전체 정의
7. 호출되는 모달 동작
8. 토스트와 확인 팝업과 알럿
9. 데이터 흐름과 외부 연동
10. 화면 상태와 예외 처리
11. 권한별 처리
12. 메인 흐름 (Mermaid)
13. 에러와 예외 흐름 (Mermaid)
14. 핵심 디자인 요청사항
15. 운영 정책 (이 화면에 연결된 부분)

탭이 없는 화면(예: 단순 로그인 페이지)에서는 5번 섹션이 "이 화면에는 별도의 탭이 없습니다"라는 식으로 명시적으로 짧게 적혀 있어야 하며, 섹션 자체가 사라져서는 안 됩니다.

## 4. 자기완결 원칙 검증

외부 문서나 경로로 미루는 표현이 남아 있는지 검색합니다. 다음 키워드로 grep해서 발견되는 모든 사례를 정리한 뒤, 그 자리에 원문 내용을 직접 풀어 써서 자기완결성을 회복합니다.

- "참고", "참조", "원문", "별도 문서", "○○ 문서를 보세요"
- "../", "../../", "../../../" (상대 경로)
- "docs/", "기능명세서/", "화면설계서/", "다이어그램/" (다른 카테고리 경로)
- "feature_codes:", "linked_screen:", "linked_dialogs:" (frontmatter 잔재)

다이얼로그 문서가 호출 화면의 다른 폴더로 점프하라고 안내하는 표현도 금지입니다. 다이얼로그 문서는 다이얼로그 단독으로도 자기완결적으로 동작 정의가 끝나야 합니다.

## 5. 권한별 처리 누락 검증

권한별 처리 섹션에 다음 9개 역할이 모두 등장하는지 확인합니다. 화면에 권한이 적용되지 않더라도, 그 사실 자체를 명시적으로 적어야 합니다.

- superAdmin (슈퍼관리자)
- primary (본사 최고관리자)
- owner (Owner(지점장))
- manager (매니저)
- fc (피트니스 코치)
- trainer (트레이너)
- staff (스태프)
- front (프런트)
- readonly (읽기 전용)

각 역할마다 다음 4가지가 명시되어야 합니다.

- 진입 가능 여부
- 보이는 영역과 숨겨지는 영역
- 가능한 액션과 불가능한 액션
- 권한 부족 시 표시(비활성·메시지·리다이렉트)

## 6. 모달·팝업·토스트 누락 검증

화면 문서의 7번 섹션에 그 화면에서 호출되는 모든 모달이 빠짐없이 등장해야 합니다. 각 모달마다 다음 항목이 풀려 있어야 합니다.

- 모달 이름과 호출 트리거
- 모달 안의 UI 구성과 입력 필드
- 검증 규칙
- 확인 / 취소 / 닫기 각 액션의 결과
- 모달 닫힘 후 부모 화면의 변화
- ESC / 배경 클릭 동작
- 권한별 노출 차이

토스트와 확인 팝업과 알럿도 8번 섹션에 모두 정리되어 있어야 합니다.

## 7. 운영 정책 녹임 검증

15번 운영 정책 섹션에 다음 카테고리 중 그 화면에 해당하는 항목이 풀려 있어야 합니다. 항목 자체가 화면과 무관하면 생략 가능하지만, 관련이 있는데 누락된 경우에는 추가해야 합니다.

- 회원 상태 운영 정의 (D02·D11 관련 화면)
- 세그먼트 운영 기준 (D02 관련)
- 권한·책임 분리 (D07·D09·D10 관련)
- KPI 산식과 측정 주기 (대시보드·리포트 화면)
- 자동화 정책표 (D08·D09·D11 관련 + 회원 만료 알림 등)
- PII 마스킹과 감사 로그 (회원·결제·삭제·복구 화면 공통)
- 환불·미수금·세금계산서 운영 (D03 관련)
- 예약·노쇼·페널티 정책 (D04 관련)
- 락커·소모품·청소 운영 (D06 관련)
- 직원 역할·근태·급여 운영 (D07 관련)
- 리드 퍼널·자동 알림 13종·쿠폰·마일리지·전자계약 (D08 관련)
- 본사-지점 통합 모드·정책 세트 step·자동화 정책 라이브러리 (D10 관련)
- 통합 출석·키오스크 운영·IoT 연동·체성분 (D11 관련)

## 8. 카테고리 간 불일치 보정

기능명세서·화면설계서·다이어그램·운영 문서 사이의 불일치가 발견되면, 가장 최신·가장 자세한 값을 기준으로 화면 문서를 통일합니다. 다음 항목이 자주 어긋나는 지점이므로 우선 확인합니다.

- 상태 필터 탭의 항목 수와 순서 (예: 회원 목록의 상태 8개가 도메인별로 다르게 적힌 사례)
- 권한 매트릭스의 행/열 라벨(role 키와 운영 라벨의 혼재)
- 다이얼로그 ID 표기(`DLG-M001` vs `DLG-M001_상태변경`)
- 계약코드 alias 처리(MKT-02, RSV-04 등 중복 매핑)
- 자동화 배치 시각(02:00 / 03:00 / 04:00 / 05:00 정렬)
- KIOSK 연동 매트릭스의 SCR 매핑 (D09·D11 교차 검증)

## 9. Mermaid 다이어그램 렌더 검증

12·13번 섹션의 Mermaid 코드 블록이 모두 구문 오류 없이 렌더되는지 확인합니다. classDef는 도메인 전체에서 통일된 색상·라인 두께를 사용합니다. 노드 이름에 특수문자(공백·하이픈·괄호)가 포함되어 있으면 따옴표로 감싸야 합니다.

## 10. 분량 적정성 검증

문서 분량이 가이드 범위 안에 있는지 확인합니다.

- 허브 화면: 350~500줄
- 일반 화면: 250~350줄
- 다이얼로그: 150~250줄

가이드를 크게 벗어난 문서(예: 100줄 이하의 너무 짧은 허브 화면 / 800줄 초과의 너무 긴 일반 화면)는 사용자에게 사유와 함께 보고하고, 필요하면 보강 또는 압축을 진행합니다.

## 11. 최종 검수 보고

검수가 끝나면 다음 항목을 정리한 최종 보고 문서(`docs-domain/_검수_결과.md`)를 작성합니다.

- 총 문서 수와 도메인별 분포
- 평균 줄 수와 도메인별 분포
- 발견된 불일치 케이스와 보정 내역
- 사용자에게 확인 요청이 필요한 결정 사항
- 누락된 화면·다이얼로그 (있다면)
- 향후 갱신이 필요한 항목 (외부 연동·정책 결정 등)
