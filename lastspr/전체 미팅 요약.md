# 회의 요약

## **주요 논의**

- 버전 범위

  - 1.0은 우선 출시 범위 중심으로 진행.
  - 회계/정교한 손익 구조 등은 1.5로 우선순위 조정.
  - 1.0에서는 회계성 입력은 수기 입력 중심으로 가는 방향.
  - 기능이 되더라도 사용 후 UX를 개선하는 순서가 적절하다는 의견.

- 결제 후 수기 정보 입력 UX

  - 현재 온핏/브로제이에서는 결제 후 수기 입력, 영수증/승인번호 처리까지 2~3분 정도 소요.
  - 회원 상담 직후 현장에서 바로 결제/계약서 확인까지 끝내는 흐름이 이상적.
  - 개발 후 실제 사용해보고 클릭 수, depth, 중복 입력을 줄이는 방향으로 UX 개선 필요.
  - 기존 온핏/브로제이 사용자라면 30분 내 사용 가능할 것으로 보이나, 초보 직원을 위한 사용 가이드 필요.

- PT 차감/노쇼

  - DB 차감 오류 가능성은 낮으나, 핵심은 수업 완료를 어떤 방식으로 인정할지임.
  - 기존 사인/지문 방식보다 트레이너 완료 처리 후 회원 푸시 확인 방식이 더 단순하다는 의견.
  - 회원이 응답하지 않는 경우 일정 시간 이후 자동 완료 처리하는 방식이 언급됨.
  - 노쇼는 수업 전 불참 신청 마감 기준을 정책으로 정해야 함.
  - 노쇼/차감 정책은 스포짐 운영 기준으로 확정 필요 - word 파일 참고

- 부분 결제/부분 취소/미수금

  - 스포짐은 하나의 상품 또는 여러 상품을 카드 2~3개, 현금, 계좌이체 등으로 나눠 결제하는 케이스가 있음.
  - 한 화면에서 여러 결제수단/매입사별 결제를 등록하고, 취소/변경도 같은 화면에서 처리되면 좋다는 요구.
  - 카드 승인 건 자체는 기본적으로 승인금액 단위 전체 취소가 원칙으로 이해.
  - 상품 일부 취소나 결제수단 일부 취소 시 남은 금액은 미수금으로 잡혀야 함.
  - 1.0에서는 CRM에서 미수금을 관리하고, 회원앱/키오스크에서 반복 알림까지 띄우는 것은 제외하는 방향.
  - 미수금 알림은 추후 정책 결정 필요. 최소한 CRM에서 직원이 인지할 수 있어야 함.

- VAN사/PG/수수료

  - 현재 VAN사가 한국정보통신, KPN, 나이스 등으로 섞여 있음.
  - VAN사는 하나로 통일하는 것이 커뮤니케이션과 운영상 유리하다는 의견.
  - 지점별 수수료율이 다를 수 있어 실제 입금 내역/수수료 확인 필요.
  - 담당 VAN/PG 업체 미팅 또는 담당자 확인 필요.

- 환불

  - 위약금 계산식과 환불 계산기가 필요.
  - 위약금 %, 사용일수, 정상가/등록가 기준 등 환불 정책이 지점별 또는 상품별로 다를 수 있음.
  - 정산이 이미 끝난 카드 취소는 시스템 자동 처리보다 전화/수기/상계 처리에 가까운 운영 프로세스로 설명됨.
  - CRM에서는 환불/취소 내역을 기록하고, 매입 취소 자동화는 1.0 범위에서 신중하게 봐야 함.

- 계좌이체/현금영수증

  - 카드/현금 외에 계좌이체 결제수단도 필요.
  - 계좌이체 시 입금자명이 회원명과 다를 수 있으므로 입금자명 입력 필드 필요.
  - 매장 직원이 입금자명과 결제 정보를 입력하는 방식.
  - 현금영수증 처리 여부와 입력 항목 확인 필요.

- 결제내역/영수증/승인번호

  - 회원별 결제내역과 영수증/인보이스 확인 기능은 필요.
  - 승인번호는 CRM 내부에서 확인 가능해야 취소/변경 업무가 쉬움.
  - 영수증 사진/OCR 또는 POS 연동으로 승인번호 자동 입력이 되면 수기 오류를 크게 줄일 수 있음.
  - POS 내장/연동은 이상적이나 1.0 범위에서는 우선순위 조정 필요.

- 지점별 매출 귀속

  - 기본적으로 결제/등록이 발생한 주센터 또는 해당 지점에 매출을 귀속.
  - 타 지점 이용이 많아지는 경우 지점 간 매출 쉐어 정책이 필요하지만, 1.0에서는 자동 정산까지는 제외.
  - 우선 현재 운영 방식과 동일하게 가고, 향후 정책 확정 후 확장하는 방향.

- 지점 다중 소속/홈&오피스

  - 주센터/부센터 개념 필요.
  - 부센터는 출입/이용만 가능하고, 결제/매출 귀속은 주센터 중심으로 보는 방향.
  - 홈&오피스 상품은 전 지점 공통 가격 또는 본사 관리 상품으로 정리해야 단순해짐.
  - 지점별 가격이 다르면 차액 결제, 미수금, 이용 가능 지점 판단이 복잡해짐.
  - 1.0에서는 자동 가격 판단보다 매장 책임하에 선택/입력하고, CRM은 선택 가능한 구조를 제공하는 방향.
  - 프랜차이즈 단위 회원/상품 정책은 별도 정리 필요.

- 법인 회원권

  - 기명: 회원을 지정해 일반 회원처럼 관리.
  - 무기명: 회사 단위로 일괄 계약하고, QR/번호 등을 공유해 입장하는 방식.
  - 무기명은 일일 이용 가능 인원 수 제한과 카운팅 필요.
  - 제한 초과 시 CRM/점장/담당자에게 알림이 가는 구조가 필요.
  - 회원앱에서 잔여 인원까지 보여줄지는 1.0 범위를 넘길 수 있어 우선순위 조정 필요.

- 대기열/예약 제한

  - GX/그룹수업은 최대 정원 도달 시 예약 제한.
  - 취소가 발생하면 대기열 순번이 올라가고, 회원에게 알림이 가야 함.
  - 대기열 등록 시 “자리 발생 시 자동 예약될 수 있음” 또는 “참석 여부 확인 필요”를 명확히 안내해야 함.
  - 최종 자동 배정인지, 회원 확인 후 배정인지 정책 결정 필요.

- 급여/정산/지출

  - 급여 정산은 수기로 입력하고, 계약서/서식 업로드 방식으로 가는 것으로 이해.
  - 급여액 계산은 가능하나 자동 송금/완전 자동 급여 처리와는 분리.
  - 1.0에서는 지출 탭을 수기로 입력할 수 있게 하는 수준.
  - 지출 항목은 스포짐이 전달하고, 시스템은 항목별 숫자 입력 중심으로 구성.
  - 손익 구조/회계는 1.5에서 다루는 방향.

- 회원등급

  - 회원등급은 1.0~1.5에서는 제외하는 방향.
  - 누적 결제, 출석, 참여도 등 기준은 가능하지만 정책 정의가 필요하고 우선순위가 낮음.

- 마일리지

  - 마일리지는 1.0에서 기본 구조를 둘 수 있음.
  - 현재는 결제 금액의 N% 또는 고정 금액을 적립/페이백처럼 사용하는 개념.
  - 사용은 결제 시 적용하는 방식.
  - 스포짐이 적립률, 사용 기준, 소멸 기준, 지점별 허용 범위를 정책으로 정의해 전달 필요.

- 대시보드

  - 프로젝트의 핵심 취지는 운영 의사결정용 대시보드.
  - 본사/대표/회장 레벨에서 볼 통합 대시보드와 지점장용 대시보드는 구분 필요.
  - 신호등 지표는 green/yellow/red 기준, 점수 합산 방식, 가중치가 필요.
  - 지점 랭킹은 매출액, 전월 대비 상승률, 손익, 비용 등 어떤 기준으로 볼지 정해야 함.
  - 최근 활동 히스토리 등 의미가 낮은 항목은 제거 가능.
  - 스포짐에서 꼭 볼 항목을 정하고, 판도 내부에서 생략할 항목은 생략하는 방향.

- 권한/역할별 화면

  - FC, PT 트레이너, 지점장, 본사/대표 등 역할별로 볼 화면을 정해야 함.
  - 기본 권한 세트는 판도에서 제안하고, 스포짐이 선택/수정하는 방식이 적절.

- KPI/Today’s Work

  - 현재 안은 일부 지점장 아이디어가 많이 반영된 상태.
  - 1.0에서 그대로 넣을지, 테스트 형태로 둘지, 생략할지 결정 필요.
  - 통계 데이터가 충분히 쌓여야 의미 있는 KPI가 나오므로 우선순위 조정 필요.

- 온보딩/프리온보딩

  - 프리온보딩은 리드/마케팅/상담 전환 관리와 연결됨.

  - 현재 구글시트/엑셀로 관리하는 흐름을 CRM 안으로 넣는 것이 중요.

  - 신규은 신규/휴면, 재등록은 만료 임박/만료 등으로 FC가 쓰는 용어에 맞게 구성하는 것이 좋음.

  - 전화번호 기반으로 N차 온보딩을 관리하는 흐름 필요.

  - 1차/2차 유입경로, 상담, 등록 전환율과 연결되어야 함.

# 회의 요약

목적 : 질의를 통해 기획 요구사항 이해도 보완 제외사항 : 추가건인지 아닌지 여부는 이번 회의에선 논의하지 않습니다. 질의가 끝나서 내부 정리가 완료되면 추가건 관련 논의를 제로스트 대표님이 판도대표님과 함께 진행 예정

## **회의 개요**

- 회의 목적: 상세 기능 리스트, 기획 MD, 견적/계약 범위 간 불명확 항목을 확인하고 개발 범위 판단 기준을 맞추는 회의.
- 진행 방식: 제로스트가 기능별로 애매한 항목을 질의하고, 판도/기획 측이 기능 의도, 범위 판단, 추가 확인 필요 여부를 답변.
- 큰 정리 방향: 각 항목을 계약 포함 가능, 신규/추가 개발로 보임, 기획 명확화 후 판단 3가지로 구분해 후속 논의하기로 함.
- 최신 기획/TC: TC는 최신 기획에 가깝게 작성된 것으로 보고, 제로스트가 API 초안 및 TC도 함께 검토하기로 함.

## **주요 논의**

- 플랜 비교
  - 단순히 여러 플랜의 설명/차이를 UI로 보여주는 수준이면 기존 범위로 이해.
  - 플랜 변경 시 가격 효율, 추천, 기능 차이 자동 판별까지 포함하면 추가 기능 성격으로 봄.
- 직원 매핑/권한
  - 직원별 역할, 권한, 직무를 매핑해 보여주는 기능으로 이해.
  - 권한에 따라 접근 가능한 화면/메뉴가 제한됨.
  - 메뉴별 노출 권한 정의는 있는 것으로 보이며, 관련 자료를 찾아 공유하기로 함.
- 대시보드 상단 액션/환영 배너
  - 새로고침, 위젯/회원 클릭, 전체 목록 복귀 등은 UI 액션 버튼으로 이해.
  - 환영 배너는 관리자 편집/관리 기능 없이 고정 배너로 이해.
- KPI 24종
  - 산식, 일괄 처리 시각, 지표 정의가 문서상 부족.
  - 스포짐/클라이언트 확인 후 제로스트에 공유 필요.
- 상담 퍼널

  - 큰 이견은 없으나 용어가 생소할 수 있어 생소한 용어에 대해서는 카톡 등으로 즉시 질의하기로 함.
- 액션 큐

  - 모바일 알림 등 별도 후속 액션이 있는지는 현재 기획과 다를 수 있어 확인 필요.

  - 상담자와 등록자가 다른 경우, 퇴사/인수인계 시 KPI 배분도 확인 필요.

# 회의 요약

이번 회의는 회원 앱·CRM 구조, 결제 흐름, 디자인 범위, 대시보드 확정, 외부 연동 범위를 빠르게 정리하는 데 초점이 있었습니다.

## **회의 개요**

- 회의는 회원 앱과 CRM을 중심으로 Q&A 방식으로 진행됐고, 앞으로 용어도 “회원 앱”과 “CRM”으로 통일해서 쓰자는 방향이 잡혔습니다.
- FC와 스태프 기능은 모두 범위에 포함하는 쪽으로 정리됐고, 필요한 API는 기능 단위로 구체적으로 정의해서 요청해야 한다는 점이 강조됐습니다.
- 현재 화면만으로는 구조 이해가 어려워서, 역할 정의·정책·히어라키·관리 구조를 문서로 받아야 한다는 요구가 분명하게 나왔습니다.

## **핵심 논의**

- CRM은 현재 퍼블리싱 변경 과정에서 구조가 뒤섞여 있어, 실제 정책과 운영 구조를 화면만 보고 파악하기 어렵다는 문제가 공유됐습니다.
- 대시보드는 이번 주 안에 우선 고정해서 스포짐 측이 화면을 보고 넣을 것과 뺄 것을 결정해야 다음 일정 지연을 막을 수 있다는 의견이 나왔습니다.
- 모바일 디자인은 아직 최종 디자인 산출물로 보기 어렵고, 현재 자료는 기획·퍼블리싱 중간 단계에 가깝다는 인식이 공유됐습니다.
- 헬스커넥트는 모바일 웹으로는 불가능하고 네이티브 앱이 필요하다는 기술 검토가 나왔으며, 현재 일정 안에서는 1차 버전 제외 의견이 우세했습니다.

## **결정·정리 사항**

- 키오스크 결제는 현재 범위에서 제외하는 쪽으로 정리됐고, 결제는 FC 처리와 회원 휴대폰 결제 중심으로 보는 흐름이었습니다.
- 본사와 지점은 현재 구조상 함께 관리되지만, 실제 운영에서는 본사도 지점 형태로 설정되어 있는 것으로 설명됐습니다.
- 회원은 한 번에 한 지점에 소속되는 구조로 이해됐고, 다른 지점 이용은 이전 절차로 처리하는 방향이 언급됐습니다.
- 골프 타석 사전 예약은 스포짐에서는 우선순위가 낮지만, 다른 브랜드를 고려하면 매장별 on/off 설정이 가능해야 할 수 있다는 의견이 나왔습니다.
- 커뮤니티 기능은 필요성이 높게 언급됐고, 특히 CRM 안에서 게시판·모임장·관리자 권한 구조를 어떻게 둘지 추가 설계가 필요하다고 정리됐습니다.
