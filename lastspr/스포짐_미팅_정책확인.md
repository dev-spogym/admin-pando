## 1. 검토 결론

현재 문서 기준으로는 **1.0은 “수기 입력 + 상태관리 + 알림/이력 중심”으로 가는 방향이 맞습니다.**

다만 스포짐 미팅에서 논의된 내용 중 운영정책이 아직 문서에 충분히 반영되지 않았거나, 현재 문서와 방향이 충돌하는 항목이 있습니다. 이 항목들은 개발자가 임의 판단하면 안 되며, `정책미확정/후속논의`로 분리해 고객사 또는 판도 내부 기준을 확정한 뒤 반영하는 것이 안전합니다.

특히 바로 정리해야 할 핵심은 아래 5개입니다.

1. **주센터/부센터 정책**
2. **수업 완료 방식: 전자서명 유지 여부 vs 회원앱 Push 확인 중심 전환**
3. **할인/프로모션 본사 승인 정책**
4. **법인회원권 일일 입장 제한 및 초과 처리**
5. **PIN 기반 실제 처리자 기록 정책**

## 3. 현재 문서에 이미 어느 정도 반영된 내용

아래 항목은 현재 버전에서 기본 구조가 이미 들어가 있어, 큰 방향은 유지해도 됩니다.

### 3.1 결제 / 매출

- 혼합결제 / 분할 수납 기본 구조
  - `docs2/D03-매출관리/매출관리.md`의 `SCR-S003 결제 처리`
- 현장 POS 직접 승인 대신 외부 POS/현금/계좌이체 처리 후 CRM에 영수증 기반 등록
- 결제수단별 수납 행 입력
- 결제수단, 금액, 승인번호 또는 이체확인번호, 승인시각, 영수증 파일, 메모 저장
- 수기 할인 입력
- 계약금 등록, 잔액 등록, 미수금 또는 할부 계획 연결

### 3.2 환불 / 부분 환불 / 미수금

- 수기 입력 기반 환불 / 부분 환불
  - `SCR-S012 결제 취소 / 부분 환불`
  - `DLG-S013 환불 처리`
- 환불 자동 산식은 미확정으로 두고, 기사용 차감금·위약금·기환불 누계·최종 환불액을 수기 입력
- Owner(지점장) 승인 또는 manager/fc 승인 요청 구조
- 미수금 관리
  - `SCR-S008 미수금 관리`

### 3.3 회원 상세 / 계약 액션

- 회원 상세 내 결제/환불/양도/홀딩 액션
  - `SCR-M004 회원 상세`
- 양도/양수 기본 기능
  - `DLG-M019 양도 처리`
- 가족 회원 연결
  - `SCR-M008 가족 회원`
- 마일리지 조정
  - `DLG-M021 마일리지 조정`

### 3.4 수업 / 예약 / 노쇼 / 대기열

  - `SCR-C008 페널티 관리`
- 대기열 관리
  - `SCR-C012 대기열 관리`
- 수업 출석/완료 확인
  - `CLS-14`, `/attendance/lesson-completion`

### 3.5 상품 / 시설 / 재고

- 상품 관리에서 회원권, 수강권, 락커, 운동복, 일반 상품 구분

## 4. 정책이 빠졌거나 보강 필요한 항목

## A. 1.0 현재 버전에 바로 반영 또는 정리해야 할 가능성이 높은 항목

### 4.1 계좌이체 입금자명

**미팅 요구**

- 계좌이체 시 `입금자명`을 별도로 입력할 수 있어야 함.

**현재 문서 상태**

- 결제 행에는 아래 항목이 있음.
  - 결제수단
  - 금액
  - 승인번호 또는 이체확인번호
  - 승인시각
  - 영수증 파일
  - 메모
- 하지만 `입금자명` 필드가 명시돼 있지 않음.

**판단**

- 누락입니다.
- 1.0 결제 입력 필드에 추가하는 것이 좋습니다.

**정리 필요**

- 계좌이체 결제수단 선택 시 입금자명 필수 여부
- 회원명과 입금자명이 다를 때 표시 방식
- 입금자명 기준 검색/필터 필요 여부

---

### 4.2 주센터 / 부센터 용어와 정책

> 해당 기획은 후순위로 판단

**미팅 요구**

- 주센터: 등록/결제 기준 센터
- 부센터: 추가 이용 가능 센터
- 홈앤오피스, 전지점 이용권, 주말 이용권, 법인권 등에서 주센터/부센터 구조 필요

**현재 문서 상태**

- 현재 문서에는 다음 용어가 있음.
  - 소속지점
  - 기본 이용지점
  - 이용 가능 지점
  - 결제지점
  - 이용지점
  - 매출 귀속 지점
  - 정산 지점
- 하지만 `주센터`, `부센터`라는 용어는 명시적으로 거의 없음.

**판단**

- 스포짐 운영 용어와 현재 기획 용어가 다릅니다.
- 용어 매핑이 필요합니다.

**정리 필요**

- 주센터 = 소속지점인지, 결제지점인지, 기본 이용지점인지 확정
- 부센터 = 이용 가능 지점 중 보조 지점인지 확정
- 부센터에서 가능한 액션 범위
  - 조회
  - 입장
  - 상담
  - 결제
  - 환불
  - 양도
  - 홀딩
- 전지점 이용권의 조회/입장 범위
- 홈앤오피스의 부센터 개수 제한

### 4.3 법인회원권 일일 입장 제한

> 해당 기획은 후순위로 판단

**미팅 요구**

- 기명 법인권 / 무기명 법인권 구분
- 회사 단위로 하루 입장 가능 인원 또는 횟수 제한
  - 예: A 회사 하루 10명까지

- 초과 시 차단할지, 관리자 알림만 띄울지 정책 필요

**현재 문서 상태**

- `기명법인`, `무기명법인`, `법인 회사명` 입력은 있음.
- 법인권 매출, 세금계산서, 법인 환불 안내도 있음.
- 하지만 회사 단위 일일 입장 제한, QR 발급 방식, 초과 처리 정책은 부족함.

**판단**

- 법인권 기본 구분은 반영됐으나 운영정책은 스포짐 정책 정리 후 기획하여야 합니다.

**정리 필요**

- 법인권 등록 단위
  - 회사 단위
  - 회원 단위
  - 계약 단위
- 기명/무기명 구분 기준
- 무기명 법인권 QR 또는 식별값 발급 방식
- 일일 입장 제한 기준
  - 인원 수
  - 횟수
  - 지점별/전체 합산
- 초과 시 처리
  - 입장 차단
  - 관리자 승인 후 입장
  - 경고만 표시
- 회원 앱 노출 여부

### 4.4 수업 완료 방식: 전자서명 vs Push 확인

**미팅 요구**

- 전자서명 이미지 저장보다 `트레이너 완료 처리 → 회원 앱 Push 확인` 방식이 더 적합하다는 의견
- 회원이 확인하지 않더라도 일정 시간이 지나면 자동 완료 처리 검토

**현재 문서 상태**

- 현재 `DLG-C006 서명`에는 서명 패드, 서명 이미지 저장, 서명 이미지 암호화가 남아 있음.
  - 

- 동시에 회원앱 Push 확인도 포함되어 있음.

**판단**

> 해당 내용은 Push 확인 버튼으로 진행하기로 하였으나 재확인은 해보아야함.

- 미팅 방향과 현재 문서가 일부 충돌합니다.
- 전자서명을 유지할지, Push 확인 중심으로 전환할지 결정 필요합니다.

**정리 필요**

- 1.0에서 전자서명 패드를 유지할지 여부
- 서명 이미지 저장 필요 여부
- 회원앱 Push 확인을 기본으로 할지 여부
- 회원 미확인 시 자동 완료 기준 시간
- 이의제기 가능 기간
- 수업 차감 시점
  - 트레이너 완료 시
  - 회원 확인 시
  - 자동 완료 시

### 4.5 할인 / 프로모션 본사 승인 구조

**미팅 요구**

- 지점에서 임의 할인하면 위험함.
- 할인권/프로모션 상품 생성 시 본사 승인 필요.
- 승인 전에는 현장 결제 화면에 노출되지 않아야 함.

**현재 문서 상태**

- D05 할인 설정은 할인 정책 등록·수정·삭제·조회 구조가 있음.
- Owner/manager도 할인 정책 등록·수정·삭제 가능하게 보이는 부분이 있음.
- 결제 화면 자동 적용은 v1 제외로 정리되어 있음.
- 하지만 “지점 생성 → 본사 승인 → 노출” workflow는 명확하지 않음.

**판단**

- 승인 정책이 부족하거나 현재 문서와 미팅 방향이 충돌할 수 있습니다.

**정리 필요**

- 본사 할인과 지점 할인 구분
- 지점 할인 생성 가능 여부
- 승인 전 상태
  - 임시저장
  - 승인대기
  - 반려
  - 승인완료
- 승인자 권한
- 승인 전 결제 화면 노출 여부
- 프로모션 상품과 할인권의 차이
- 사용 횟수 제한 / 기간 제한 / 대상 상품 제한

### 4.6 상품별 매출 귀속 부서

**미팅 요구**

- 상품이 FC 매출인지, PT 매출인지, 골프 매출인지, 기타 매출인지 구분 필요
- 부서별/담당자별 매출 통계 필요
- 향후 급여/인센티브와 연결

**현재 문서 상태**

- 결제지점, 이용지점, 매출 귀속 지점, 정산 지점, 인센티브 귀속자는 있음.
- 하지만 상품별 `매출 귀속 부서` 기준은 약함.

**판단**

- 부서 귀속 정책 누락입니다.

**정리 필요**

- 상품 등록 시 매출 귀속 부서 필수 여부
- 부서 코드
  - FC
  - PT
  - GX
  - 골프
  - 락커
  - 운동복
  - 일반 상품
  - 기타
- 상품별 담당자와 부서 귀속이 다를 때 우선순위
- 매출 통계/급여/인센티브 연결 기준

### 4.7 PIN 기반 실제 처리자 기록

> 해당 기획은 후순위로 판단

**미팅 요구**

- 지점장 계정으로 로그인한 PC를 여러 직원이 같이 쓰는 경우가 있음.
- 결제, 수정, 할인, 담당자 변경 등 주요 액션 시 직원별 PIN 입력.
- 실제 처리자를 기록해야 함.
- 예 . 사용자가 A로 로그인되어있는데 B가 상담 등록을 시켜주어, 실제 인센티브를 받아가는인원이 B가 되도록 빠르게 변경하기 위함. 

**현재 문서 상태**

- 히스토리 로그는 있음.
- 변경 전/후, actor, 사유 기록 구조도 일부 있음.
- 하지만 `PIN` 기반 처리자 식별 정책은 없음. 
  - PIN 을 직접 진행할지 판도와 논의 하기로하였음. 


**판단**

- 중요한 감사 정책 누락입니다.

**정리 필요**

- PIN 입력이 필요한 액션 범위
  - 결제 등록
  - 환불 요청/승인
  - 할인 입력
  - 회원 정보 수정
  - 담당자 변경
  - 양도/양수
  - 홀딩/해제
  - 출석 수동 처리
  - 재고 조정
- PIN 실패 횟수 제한
- PIN과 로그인 계정의 관계
- 처리자와 승인자를 별도 기록할지 여부
- PIN 없이 처리 가능한 예외 상황

### 4.8 미수금 알림 정책

## 7. 최종 요약

스포짐 미팅 내용은 현재 기획 문서와 큰 방향은 맞습니다.

현재 기획은 이미 아래 방향으로 정리되어 있습니다.

- 현장 결제는 외부 POS/현금/계좌이체 처리 후 CRM에 등록
- 환불은 자동 산식이 아니라 수기 입력 + 승인 중심
- 미수금은 CRM에서 상태 관리
- 회원 상세에서 환불/양도/홀딩 등 주요 액션 처리
- 수업 노쇼/대기열/차감은 기본 구조 제공
- KPI와 Today Tasks는 기본 지표 중심
  - 다만, 마지막에 KPI, Today Tasks 를 제외한다는 말이 오감..
