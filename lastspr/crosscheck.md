# 스포짐 기획 필수 정책 문의 정리

대상 시트: `3.CRM (admin)_제로스트_0518논의`
확인 범위: 시트 4~751행, `docs2` 기획/운영정책 기준 대조
작성 목적: 기능 구현 여부가 아니라, 스포짐 운영 정책값이 있어야 기획을 확정할 수 있는 질문만 정리

## 스포짐 운영 정책 확인 방식

이 문서는 기능 추가 여부를 묻기 위한 문서가 아니라, CRM 화면/상태값/자동화/권한을 확정하기 위해 필요한 스포짐 운영 정책 확인 문서입니다.
`HQ-09`, `RBAC`, `액션 큐`, `SLA` 같은 내부 기획 용어는 그대로 묻지 않고, 실제 현장 운영 상황 기준으로 풀어서 확인합니다.

1. 기능 배경: 해당 기능이 실제 운영에서 어떤 상황에 쓰이는지 설명합니다.
2. 현재 임시 기획 기준: 판도 기획에서 우선 잡아둔 기준입니다. 확정 정책이 아니라, 스포짐 답변 전까지의 기준안입니다.
3. 확인할 질문: 실제 운영 정책으로 확정해야 하는 질문입니다.
4. 기획에 필요한 이유: 답변이 없을 때 화면/자동화/권한/상태값 중 무엇이 확정되지 않는지 설명합니다.

## 용어 설명

아래 용어는 문서 안에서 반복해서 나오기 때문에, 먼저 뜻을 맞추고 확인합니다.

| 용어 | 설명 |
|---|---|
| CRM | 회원, 상담, 결제, 수업, 직원, 지점 운영을 관리하는 관리자 시스템입니다. |
| RBAC / 권한 체계 | 역할별로 볼 수 있는 화면과 처리할 수 있는 기능을 나누는 기준입니다. 예: 본사 관리자, 지점장, 상담 담당자, 트레이너별 권한 구분 |
| KPI | 매출, 재등록률, 출석률처럼 지점/직원/운영 성과를 판단하는 핵심 지표입니다. |
| 액션 큐 | 오늘 처리해야 할 업무를 우선순위로 모아 보여주는 목록입니다. 예: 상담 미처리, 재등록 상담 대상, 미수금 확인 |
| SLA | 업무를 언제까지 처리해야 하는지에 대한 내부 처리 기준입니다. 예: 일정 요청이 들어온 뒤 몇 시간 안에 답변해야 하는지 |
| HQ-09 | 본사에서 관리하는 자동 알림 정책 묶음을 임시로 부르는 내부 코드명입니다. 실제 확인 시에는 “만료/결제기한/라커 만료 알림 정책”으로 보면 됩니다. |
| FC | 상담 및 등록을 담당하는 직원입니다. 전화 문의, 방문 상담, 등록 전환, 재등록 상담을 담당합니다. |
| PT | 1:1 퍼스널 트레이닝 수업입니다. |
| GX | 요가, 필라테스, 스피닝처럼 여러 회원이 함께 참여하는 그룹수업입니다. |
| QR | 회원 앱 등에서 보여주는 코드로, 출입 확인이나 보조 인증에 사용할 수 있는 방식입니다. |
| Push | 회원 앱으로 보내는 알림입니다. |
| fallback | 기본 알림 방식이 실패하거나 사용할 수 없을 때 보조 채널로 보내는 방식입니다. 예: 앱 알림이 어려우면 카카오톡으로 보조 발송 |
| VAN / 카드사 연동 | 카드 결제 승인·취소 데이터를 카드 단말기/결제대행사와 시스템으로 연결하는 방식입니다. |
| PIN | 공용 PC에서 실제 처리 직원을 확인하기 위해 직원별로 입력하는 짧은 인증번호입니다. |
| API | 외부 시스템과 데이터를 자동으로 주고받기 위한 연결 방식입니다. 예: 라커 시스템, 카드 사용 내역, InBody 데이터 연동 |
| ERP / 그룹웨어 | 지출, 결재, 회계, 내부 승인 등을 관리하는 별도 업무 시스템입니다. |
| D-30 / D-7 / D-Day / D+1 | 기준일 전후 알림 시점입니다. 예: D-7은 만료 7일 전, D-Day는 만료 당일, D+1은 만료 다음 날입니다. |

| 우선순위 | 의미 | 문의 묶음 |
|---|---|---|
| P0 | 답이 없으면 화면 기준/상태값/자동화가 확정되지 않음 | 권한/민감기능, 결제/혼합결제/부분취소/미수금/환불, 수업 차감/노쇼, 액션 큐, 핵심 지표/성과, 주센터/부센터, 양도/양수/홀딩/연기, 할인/프로모션 승인, 자동화 정책 세트, 대량 발송, 데이터 마이그레이션 |

## 미팅 내용 반영 기준

아래 문의는 최근 미팅 내용까지 반영해 다시 정리했습니다.

- 미팅에서 이미 방향이 나온 항목은 `미팅에서 확인된 방향`으로 먼저 적었습니다.
- 그래도 기획 확정에 필요한 세부값은 `스포짐에 확인할 질문` 또는 `확인을 위해 필요한 질문`으로 남겼습니다.
- 질문은 “기능을 넣을까요?”가 아니라 “스포짐 운영 기준을 어떤 값으로 확정할까요?”에 맞췄습니다.
- 기획 용어가 그대로 전달되지 않도록, 각 질문은 가능한 한 실제 현장 상황 기준으로 풀어 썼습니다.

## 1. 권한/민감 기능 운영 기준

기능 배경:
- 관리자 CRM에는 본사 관리자, 지점장, 매니저, FC, 트레이너, 스태프처럼 여러 역할이 접속합니다.
- 역할마다 볼 수 있는 메뉴와 처리할 수 있는 업무가 달라야 하며, 환불/급여/권한 변경 같은 민감 업무는 더 강하게 제한해야 합니다.

역할명 설명:
- `superAdmin`: 전체 시스템을 관리하는 최고 관리자입니다. 본사/전 지점 권한, 권한 설정, 민감 기능까지 관리할 수 있는 최상위 권한으로 보고 있습니다.
- `primary`: 본사 운영 관리자입니다. 최고 관리자는 아니지만 본사 정책, 전 지점 운영 현황, 주요 설정을 관리하는 권한으로 보고 있습니다.
- `owner`: 지점장입니다. 특정 지점의 운영 책임자로, 소속 지점 직원/회원/수업/매출 운영을 관리하는 권한으로 보고 있습니다.
- `manager`: 지점 매니저입니다. 지점장보다 낮은 운영 관리자이며, 일상 운영 처리와 일부 승인/수정 업무를 담당하는 권한으로 보고 있습니다.
- `fc`: 상담/등록 담당자입니다. 전화 문의, 방문 상담, 등록 전환, 재등록 상담 등 회원 유입과 상담 후속 조치를 담당하는 권한으로 보고 있습니다.
- `trainer`: 트레이너/강사입니다. 본인 수업, 담당 회원, 출석/수업 완료 처리 등을 중심으로 사용하는 권한으로 보고 있습니다.
- `staff`: 현장 스태프입니다. 안내데스크, 현장 지원, 단순 조회/처리 업무를 담당하는 권한으로 보고 있습니다.
- `readonly`: 조회 전용 사용자입니다. 데이터를 볼 수는 있지만 생성/수정/삭제는 하지 못하는 권한으로 보고 있습니다.

현재 임시 기획 기준:
- 기본 역할은 `superAdmin`, `primary`, `owner`, `manager`, `fc`, `trainer`, `staff`, `readonly` 8종입니다.
- 권한은 페이지 접근, 조회, 수정, 승인, 일괄처리로 나누어 봅니다.
- 민감 기능은 회원 영구 삭제, 환불 처리, 급여 확정/지급, 슈퍼관리자 권한 부여/회수, 데이터 복원, 감사로그 내보내기 등으로 정의되어 있습니다.

기능 배경:
- 회원 등급과 세그먼트는 회원을 운영 기준에 따라 자동 분류해 상담, 재등록, 쿠폰, 마케팅 발송 대상 선정에 쓰는 기능입니다.

## 6. 수업 예약/출석/노쇼/페널티 정책

기능 배경:
- 수업 예약/출석/노쇼 정책은 회원이 예약한 수업을 언제 취소할 수 있는지, 결석 시 횟수나 페널티를 어떻게 처리할지 정하는 기준입니다.
- 이 기준은 회원 이용권 차감, 강사 정산, 페널티 관리, 회원 알림에 직접 연결됩니다.

미팅에서 확인된 방향:
- 1.0에서는 전자서명 이미지보다 트레이너 완료 처리 후 회원 앱 푸시 확인 방식이 더 적합하다는 의견이 있었습니다.
- 회원이 확인하지 않아도 일정 시간이 지나면 자동 완료 처리하는 방식이 검토되었습니다.
- GX/그룹수업은 정원, 대기 순번, 취소 발생 시 대기자 자동 배정 정책이 필요합니다.

현재 임시 기획 기준:
- 수업 유형과 강습 세션 유형은 PT/GX/골프/기타 4종입니다.
- GX 세부종목은 요가/필라테스/스피닝/줌바/GX 기타 5종입니다.
- 예약형 수업 횟수 차감은 출석 확정 후 1회 차감입니다.
- QR은 수업 출석 인증용이 아니라 지점 입/출입 확인 수단으로 정정했습니다.

스포짐에 확인할 질문:
1. 수업 예약 취소 가능 마감 시간은 수업 시작 몇 시간/분 전인가요?
   - 기획파트 잠정 답변: 취소 마감 시간값 자체는 스포짐 운영 정책값으로 남겨둡니다. 다만 현 기획 기준에서 `늦은 취소`는 노쇼/페널티 대상이 아니며, 정책 위반 취소 요청은 승인 필요 상태로 처리합니다.
2. 취소 마감 이후 취소는 노쇼로 보나요, 별도 지각/취소 상태로 보나요?
   - 기획파트 잠정 답변: 별도 취소/승인 필요 상태로 봅니다. 취소 요청 거절만으로는 페널티를 부과하지 않고, 실제 미출석이 출석 인정 마감 이후까지 미처리된 경우에만 노쇼로 확정합니다.
3. 노쇼 자동 처리 기준은 무엇인가요?
   - 예: 출석 인정 마감 + N분 경과 후 자동 노쇼
   - 기획파트 잠정 답변: 출석 인정 마감 + 지점 노쇼 유예 N분 기준입니다. 기본값은 30분이며, N분이 미설정이면 자동 노쇼를 보류하고 수동 처리 대상으로 남깁니다.
4. 첫 노쇼 면제 정책이 필요한가요?
   - 기획파트 잠정 답변: `신규 회원 첫 노쇼 면제`는 본사 정책 세트에서 관리하는 예외 정책으로 반영합니다. 정책 ON이면 첫 노쇼는 경고/라벨만 표시하고 노쇼 카운트와 페널티를 증가시키지 않습니다.
5. 노쇼 시 횟수 차감, 페널티 부과, 예약 제한 중 어떤 조치를 적용하나요?
   - 기획파트 잠정 답변: 노쇼 처리된 예약 회차는 사용 처리하고, 자동 페널티 정책 ON이면 페널티를 부과합니다. 페널티 내용은 예약 제한 기본 7일, 노쇼 회차 사용 처리, 또는 병행 적용을 지원합니다.
6. 페널티 누적 시 예약 제한 기준은 어떻게 되나요?
   - 기획파트 잠정 답변: 누적 노쇼 기준 추가 페널티를 지원합니다. 현 기획 기본값은 월 3회 이상 노쇼 시 추가 페널티이며, 추가 페널티 기본값은 예약 제한 14일입니다. 1회/누적 3회/누적 5회 기준으로 단계별 페널티를 둘 수 있습니다.
7. 강사/운영자가 수동으로 노쇼를 취소하거나 정상 출석으로 정정할 수 있나요?
   - 기획파트 잠정 답변: 가능합니다. Owner(지점장) / 매니저는 노쇼 정정과 페널티 해제를 할 수 있고, 트레이너는 본인 담당 수업 범위의 출석/노쇼 처리가 가능합니다. FC/스태프는 출석 처리 보조는 가능하지만 노쇼 정정은 불가 기준입니다.
8. 회원이 수업 일정 변경/예약 요청을 했는데 직원이 처리하지 않은 경우, 몇 시간 이상 지나면 “처리 지연”으로 봐야 하나요?
   - 기획파트 잠정 답변: 24시간 초과 미처리를 SLA 초과로 봅니다. 처리 상태가 `대기` 또는 `응답대기`인 요청이 24시간을 넘으면 별도 배지와 Today Tasks 항목으로 노출합니다.
9. 위 처리 지연이 발생했을 때 책임자 또는 확인자는 담당 강사, 지점장, 매니저 중 누구인가요?
   - 기획파트 잠정 답변: Owner(지점장)+에게 자동 에스컬레이션합니다. 운영 화면에서는 지점장/매니저가 미처리 요청을 확인하고 처리하는 기준입니다.
10. 수업 출석 완료는 트레이너 처리 + 회원 확인/서명 기준으로 확정하고, QR은 수업 출석에 사용하지 않는 기준이 맞나요?
   - 기획파트 잠정 답변: 맞습니다. QR은 수업 출석 인증용이 아니라 지점 입/출입 확인 수단으로 정리합니다. 수업 출석/완료는 트레이너 또는 권한자 처리와 회원 확인/서명 상태를 기준으로 관리합니다.
11. 트레이너가 수업 완료 처리 후 회원에게 푸시 확인을 보내는 흐름을 1.0 기준으로 확정해도 되나요?
   - 기획파트 잠정 답변: 확정 기준입니다. 전자서명 이미지 중심보다 트레이너 완료 처리 후 회원앱 Push 확인 흐름을 1.0 기준으로 둡니다.
12. 회원이 푸시 확인을 하지 않으면 몇 시간/며칠 후 자동 완료 처리하나요?
   - 기획파트 잠정 답변: 자동 완료 처리 흐름은 반영하되, 정확한 자동 완료 시간값은 스포짐 확정값이 필요합니다. 확정 전에는 `확인 대기 중` 상태를 유지하고 권한자가 수동 보정할 수 있게 둡니다.
13. 회원이 수업 완료에 이의를 제기할 수 있는 기간은 며칠인가요?
   - 기획파트 잠정 답변: 이의 제기 기간값은 스포짐 정책값으로 확인이 필요합니다. 시스템은 완료/정정 이력과 사유를 남길 수 있게 구성합니다.
14. 수업 차감 시점은 트레이너 완료 처리 시점인가요, 회원 확인 시점인가요, 자동 완료 시점인가요?
   - 기획파트 잠정 답변: 예약형 수업 횟수 차감은 `출석 확정 후 1회 차감`으로 통일합니다. 출석/완료가 확정되지 않은 `확인 대기` 상태에서는 최종 차감 확정으로 보지 않습니다.
15. GX/그룹수업 대기 가능 인원은 몇 명인가요?
   - 기획파트 잠정 답변: 대기열 기능은 반영하지만 대기 가능 최대 인원 수는 스포짐 정책값입니다. 시스템은 수업별 대기자 목록과 순번을 관리할 수 있게 둡니다.
16. 취소자가 발생하면 대기 1번을 자동 예약 처리하는 기준이 맞나요?
   - 기획파트 잠정 답변: 맞습니다. D10 본사 정책의 대기열 자동 알림/배정 정책이 ON이고, 대기 1번 회원이 자동 배정에 동의한 경우 자동 예약 처리합니다. 정책 OFF 또는 미동의이면 수동 배정합니다.
17. 자동 예약 처리 시 회원에게 사전 동의를 받아야 하나요?
   - 기획파트 잠정 답변: 받아야 합니다. 대기 상태는 `자동 배정 동의`와 `알림만`을 구분하며, 자동 배정 미동의자는 자동 예약하지 않고 다음 순번을 확인합니다.
18. 수업 시작 직전 몇 분 전까지 대기 자동 전환을 허용하나요?
   - 기획파트 잠정 답변: 자동 전환 마감 시간값은 스포짐 정책값으로 확인이 필요합니다. 확정 전에는 대기 자동 배정 정책 ON/OFF와 자동 동의 여부까지만 기획 기준으로 둡니다.
19. 대기 자동 배정 후 회원이 취소하면 노쇼/페널티가 적용되나요?
   - 기획파트 잠정 답변: 자동 배정 후에는 일반 예약과 동일하게 취소/출석/노쇼 정책을 적용합니다. 다만 취소 요청 자체만으로는 페널티를 부과하지 않고, 출석 인정 마감 + 노쇼 유예 기준을 충족한 미출석 건만 노쇼/페널티 대상입니다.

기획에 필요한 이유:
- 예약 취소 차단, 출석/노쇼 상태값, 페널티 화면, 자동화 정책, 수업 완료 기준이 확정됩니다.

## 8. 직원 근태/급여/퇴사/인수인계 정책

기능 배경:
- 직원 관리는 직원 등록, 근태, 급여, 명세서 발송, 퇴사 처리와 인수인계를 관리하는 기능입니다.
- 실제 운영 기준이 없으면 지각/급여/퇴사 후 담당 회원 이관/성과 귀속이 모두 임시값으로 처리됩니다.

미팅에서 확인된 방향:
- 1.0에서 급여 자동 송금까지는 범위가 크고, 직원별 수기 입력 및 급여 확인용 데이터 관리가 현실적입니다.
- 직원 관리에는 계약서 업로드, 기본급, 인센티브 요율, 매출 구간별 요율, 수업 차감 기준이 필요할 수 있습니다.
- 상품별 부서/담당자 매출 귀속은 향후 급여/인센티브 산정과 연결됩니다.

현재 임시 기획 기준:
- 직원 지각 기본값은 정규 출근 시각 + 10분입니다.
- 급여는 당월 미확정 상태에서 편집 가능하고, 전월 이전은 read-only 마감 월로 봅니다.
- 퇴사 처리는 `Owner(지점장)+` 권한으로 제한합니다.
- 퇴사 시 인수인계 대상 미지정은 진행 차단으로 기획되어 있습니다.

스포짐에 확인할 질문:
1. 직원 지각 기본값 10분이 실제 운영 기준과 맞나요?
   - 기획파트 잠정 답변: 현 기획 기준은 직원 직무값과 권한 역할을 분리하고, 근태/급여/퇴사 처리는 승인자와 이력을 남기는 것입니다. 이 질문은 급여 산식과 인수인계 범위 같은 회사 운영값을 확인하기 위한 항목입니다.

- 지점은 본사 정책을 그대로 쓰거나, 허용된 범위 안에서 추가 알림을 설정할 수 있습니다.

- 회원 이용권 만료와 락커 만료는 본사 step + 지점 추가 step을 허용하고, 결제기한 만료는 본사 step만 사용합니다.
- 지점은 본사 step ON/OFF를 Owner(지점장) 권한으로 제어합니다.

## 11. 쿠폰/마일리지 정책

기능 배경:
- 쿠폰/마일리지는 회원 재등록, 생일, 이벤트, 리퍼럴 보상, 환불 복원 등에 사용되는 혜택 관리 기능입니다.
- 자동 발급 여부와 환불 시 복원 기준이 없으면 결제/마케팅/회원 혜택 정책이 서로 충돌할 수 있습니다.

미팅에서 확인된 방향:
- 스포짐은 현재 포인트/마일리지를 적극 운영하고 있지는 않지만, 재등록/소개/출석/프로모션 활용 가능성이 있습니다.
- 1.0에서는 온라인몰 연동보다 회원권 재등록/결제 시 마일리지 사용 정도를 우선 검토하는 방향입니다.
- 회원 앱에서 보유 포인트/마일리지 확인이 필요할 수 있습니다.

현재 임시 기획 기준:
- 쿠폰은 활성/만료/중단 상태를 사용합니다.
- 발급 안내 메시지, 생일 쿠폰 자동 발급, 환불 시 쿠폰/마일리지 복원은 스포짐 운영 기준 확인 대기 성격이 있습니다.

현재 임시 기획 기준:
- 알림 채널은 회원 앱 알림, 카카오톡, 문자 3종입니다.

- Health Connect는 회원앱에서 회원이 직접 동의/연결하는 조회성 데이터로 봅니다.

## 16. 결제/혼합결제/부분취소/미수금/환불 계산 정책

기능 배경:
- 현장에서는 한 상품을 카드 여러 장, 계좌이체, 현금, 미수금으로 나누어 처리하는 경우가 있습니다.
- 결제 후 일부 카드만 취소하거나, 취소 후 다른 결제수단으로 재결제하는 상황도 있습니다.
- 환불은 자동 환불 처리보다 운영자가 위약금/사용분을 입력하면 계산을 보조하는 방식이 현실적입니다.

미팅에서 확인된 방향:
- 카드 다건 결제와 카드+계좌이체/현금 혼합 결제는 필요 기능으로 봅니다.
- 계좌이체에는 입금자명 입력이 필요합니다.
- 결제 건별 승인번호, 결제수단, 금액을 관리해야 합니다.
- 미수금은 CRM에서 확인 가능해야 하지만, 회원 앱 노출 여부는 별도 정책 확인이 필요합니다.
- 1.0에서는 VAN/카드사 자동 환불 연동보다 CRM 내 상태 관리와 수기 처리 보조가 현실적입니다.
- 환불 계산기는 위약금, 사용분, 사용횟수/기간을 입력해 최종 환불액을 계산하는 수준으로 검토합니다.

현재 임시 기획 기준:
- 결제는 상품 금액, 할인/마일리지, 최종 결제금액, 결제수단별 금액, 승인번호, 담당자, 결제 상태를 분리해 봅니다.
- 결제수단별 결제 건은 각각 취소/변경 대상이 될 수 있습니다.
- 상품 금액보다 결제 완료 금액이 적으면 미수금 상태로 관리합니다.
- 자동 환불은 1.0 기본 범위가 아니며, 환불 계산기와 처리 이력 중심으로 봅니다.

## 17. 주센터/부센터/전지점 이용권 정책

기능 배경:
- 스포짐은 여러 지점을 운영하며, 일부 상품은 등록 지점 외 다른 지점 이용이 가능합니다.
- 주센터/부센터 정책이 정해져야 회원 조회, 입장 가능 여부, 결제/환불 처리 권한, 지점 간 정산 범위를 정할 수 있습니다.

미팅에서 확인된 방향:
- 주센터는 회원이 등록/결제한 기준 센터로 봅니다.
- 부센터는 추가 이용 가능한 센터로 봅니다.
- 미팅에서는 1.0에서 주센터/부센터 지정과 부센터 입장 가능 처리 정도를 우선 반영하는 방향으로 정리되었습니다.
- 가격 차액 자동 계산, 센터 간 매출 자동 배분, 지점 간 정산은 1.0 필수 범위가 아니라 후속 개발 검토 항목으로 보는 방향이었습니다.

- 1.0 반영 범위와 후속 개발 사전 기준을 나누어 확인합니다.

## 19. 양도/양수/홀딩/연기/상품 종료 정책

기능 배경:
- 현장에서는 회원 상세에서 회원권/PT/골프/라커 등을 환불, 양도, 기간정지, 홀딩, 종료 처리해야 합니다.
- 이 기능은 단순 버튼이 아니라 잔여 기간/횟수, 결제/환불, 이력, 승인 권한이 함께 움직이는 정책성 기능입니다.

미팅에서 확인된 방향:
- 양도/양수는 단순 메모가 아니라 정식 기능으로 필요합니다.
- 양수 회원은 먼저 신규 회원으로 등록되어 있어야 합니다.
- 환불, 양도, 기간정지, 종료는 별도 메뉴보다 회원 상세에서 처리하는 흐름이 현장에 적합합니다.
- 상품별로 홀딩 가능 여부, 횟수, 기간이 달라질 수 있습니다.

현재 임시 기획 기준:

- 처리 이력은 삭제하지 않고 추적 가능한 상태로 남깁니다.
- 승인/사유/수정 전후값은 감사로그로 남기는 방향입니다.

## 22. 출입 인증/라커/운동복/키밴드/매장상품 정책

기능 배경:
- 출입 인증과 라커/운동복/키밴드는 현장 운영 장비와 연결되는 영역입니다.
- 장비 연동 가능 여부와 수기 대체 흐름이 정해져야 1.0 범위를 현실적으로 확정할 수 있습니다.

미팅에서 확인된 방향:
- 기본 출입은 얼굴 인식 중심, QR은 보조 수단으로 검토되었습니다.
- 전화번호 입력은 남용 가능성이 있어 신중해야 하며, 지문은 우선순위가 낮습니다.

## 23. 지출/회계/결재/ERP 연동 정책

기능 배경:
- 1.0에서도 지출 항목 수기 입력과 기본 손익 확인은 필요할 수 있습니다.
- 다만 전자결재, 그룹웨어, 은행/카드 API 연동은 CRM 안에 직접 만들지 외부 솔루션과 연동할지 결정이 필요합니다.

미팅에서 확인된 방향:
- 회계 전체 자동화는 1.5 이후 성격이 강합니다.
- 1.0에서는 지출 수기 입력, 월별 합계, 매출 대비 지출 비교 정도가 현실적입니다.

- 회원 목록, 매출 현황, 예약/출석/이용 현황은 현장 운영상 엑셀 다운로드가 필요할 수 있습니다.
- 개인정보와 매출 데이터가 포함되므로 다운로드 권한, 사유, 감사로그 정책이 필요합니다.

미팅에서 확인된 방향:
- 엑셀을 완전히 없애기 어렵기 때문에 검색/필터 결과 다운로드 기능은 필요합니다.
- 누가 언제 다운로드했는지 이력 관리가 필요합니다.
- 회원 정보 수정, 결제, 할인, 담당자 변경 등 주요 액션은 실제 처리자를 기록해야 합니다.
- 여러 직원이 하나의 PC/계정으로 사용하는 현장 이슈 때문에 PIN 기반 처리자 기록이 제안되었습니다.

현재 임시 기획 기준:
- 민감 데이터 다운로드는 권한 제한과 감사로그를 남깁니다.
- 주요 수정 이력은 누가/언제/무엇을/왜/전후값까지 남기는 방향입니다.

## 25. 베타/파일럿/데이터 검수 정책

기능 배경:
- CRM은 완성 후 한 번에 검수하기보다 실제 데이터 또는 샘플 데이터를 넣어 현장 담당자가 중간 검증해야 합니다.
- 기존 온핏/브로제/레슨북 데이터의 추출 가능 범위가 다르므로, 마이그레이션/파일럿 정책이 먼저 필요합니다.

미팅에서 확인된 방향:
- 한 지점 기준 파일럿 테스트와 실제 회원/상품/출석/결제 데이터 일부 연결이 필요합니다.
- 메모 데이터도 중요하므로 이관 가능 여부를 확인해야 합니다.
- 테스트 중 나온 피드백은 체크리스트로 관리해야 합니다.

현재 임시 기획 기준:
- 파일럿은 한 지점 또는 제한된 계정으로 시작합니다.
- 데이터 검수 완료 기준과 보류/오류 처리 목록을 둡니다.
